# 设计契约

## 何时用

- PRD 已发布，开工前需要确定接口与数据变更。
- 已有契约需要随需求变更升版。

## 步骤

1. 读 PRD 的目标、范围与验收，列出需要暴露的能力。
2. 找受影响单元：本服务、上下游服务、外部系统。
3. 定义接口：路径、方法、入参、出参、分页、错误码。
4. 定义数据变更：表结构、迁移、回滚、兼容窗口。
5. 写失败模式：超时、限流、下游不可用时的行为。
6. 产出 `contract.md`，同步给前端与 QA。

## 规则

- 契约先于实现：没有契约不让前端开工。
- 向后兼容优先：破坏性变更走平行变更（expand → migrate → contract）。
- 错误码稳定：复用已有错误码，新增要写清含义与触发条件。
- 不泄露内部结构：出参只暴露调用方需要的字段。
- 每个接口至少写一条失败路径，只写 happy path 的契约不算完成。

## 平行变更

破坏性变更分三步，不允许一步到位：

1. **Expand**：新旧两版并存，旧版不动。
2. **Migrate**：前端与调用方分批迁移。
3. **Contract**：全部迁移后再下线旧版。

## 交接

产出 `contract.md` 候选，交前端、QA、运维确认。HUMAN 发布并绑定到接收角色后，前端可以照契约写逻辑与 mock，QA 可以照契约写用例。只有流程步骤声明 `KNOWLEDGE` 输出时才能作为该任务工件交付；只声明 `IMPL` 的实现任务不授予契约发布权限。
