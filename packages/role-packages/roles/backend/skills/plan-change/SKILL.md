# 调查与实现计划

1. 固定任务快照、PRD 修订、仓库与代码版本。读取项目规范、相邻模块和已有测试，先描述现状及不允许破坏的行为。
2. 仅调查会影响本次方案的未知项。每项记录：问题、代码或官方文档依据、选定方案、放弃的方案及理由；未能确认的写 UNKNOWN。
3. 写清数据模型、接口契约、错误行为、迁移与恢复、验证命令及接收方。简单改动可直接写入 `impl.md` 前半部分，复杂改动使用 `change-plan.md`。
4. 按用户价值为多场景标 P1/P2/P3，先识别最小可用、端到端且可独立验证的 MVP 切片，并写明交付检查点；记录低优先级延期理由和恢复条件。简单改动不强制分期。
5. 按可独立验收的业务场景拆任务，每项明确 `acceptanceKeys / dependsOn / files / 验证方法`。基础依赖可先做，但计划要让首个切片尽早产生用户价值。
6. 只有无未满足依赖、文件归属不重叠的任务才标可并行；标记不授予平台外领取、执行或批准权限。
7. 对已有缺陷先记录可复现的失败或锁定当前行为；按风险安排契约和集成验证，纯文案修改不额外制造测试。
8. 核对 PRD、计划、任务、用例是否覆盖一致。可将对应数据写为质量包并运行 `workmesh quality --file quality-bundle.json --json`；通过只表示本地数据一致。

## 交接

计划保留在本次任务允许的 IMPL 正文或评审材料，契约仍走既有知识候选发布。任务拆分为提案，由现有流程确认；不得自动增加工作流步骤或修改已批准的范围。
