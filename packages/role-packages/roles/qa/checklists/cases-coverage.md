# 用例覆盖清单

- [ ] 每条验收至少一个用例。
- [ ] 用例 `covers` 引用的 key 在验收里存在。
- [ ] `kind` 与验收的 `verification` 一致。
- [ ] 边界覆盖：空值、超长、并发、权限不足。
- [ ] 异常覆盖：下游失败、超时、限流。
- [ ] 用例 ID 唯一，格式为 `TC-<需求编号>-<序号>`。
- [ ] 一条用例只验一个断言。
- [ ] 覆盖缺口已显式列出，并说明由谁、何时补。
- [ ] 不测实现细节，只测行为与契约。
- [ ] 用例设计标记未执行，不把覆盖检查当成功能通过。
- [ ] 测试执行阶段固定实现、用例与环境版本，结果可跨版本比较。
- [ ] 执行结果如实记录失败与阻塞，未执行时不声明 `cases-executed: true`。

## 交付前最后三问

1. 如果这条需求上线后出问题，现有用例能不能定位到哪个验收没过？
2. 有没有一条用例，删掉之后你依然有信心上线？如果有，它可能没用。
3. 失败分类写清楚了吗，还是全标成「产品缺陷」？

## 精确执行关联

- quality 1.1 的 cases.revision 必须引用真实 CASES 工件 ID 与 SHA-256；同一工件 ID 不能声明不同摘要。
- 每条 evidence.caseRefs 直接引用 caseId 和相同修订，acceptanceKeys 等于所引用用例 covers 的并集；全部声明用例都记录结果。
- 证据绑定同一 PRD、快照、登记仓库与完整 commit；不同仓库或提交分包。1.0 明确缺少精确关联，不补造历史修订。
- 报告、CI 提供方运行事实与 HUMAN 正式决定分别记录；本地 CONSISTENT 不证明实际执行。
