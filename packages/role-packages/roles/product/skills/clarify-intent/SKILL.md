# 澄清意图

## 何时用

- 需求刚提出，只有一句话或一段聊天记录。
- 下游发来 `NEEDS_CLARIFY`。
- 范围、参与角色或验收口径出现分歧。

## 步骤

1. **复述**：用一句话写出「谁、在什么场景、要达成什么」。
2. **划边界**：明确这次做什么、不做什么，各写三条以内。
3. **列未知**：把「假设」和「缺口」分开写，缺口要标出是否阻塞。
4. **找依据**：每条结论标注来源（知识库条目、历史需求、对话记录）。
5. **出草稿**：按 `understanding` 模板产出，交产品确认。
6. **风险排序**：扫描业务范围、数据、交互、依赖、异常与非功能要求，优先澄清会改变验收、接口、权限或兼容性的缺口；可由代码、项目资料确认的先查证。
7. **答案落地**：答案回写对应规则、范围和验收字段，列出原未知项如何消除及影响的下游产物；不得只删除问题或只记录聊天。

## 规则

- 不臆造需求：没有依据的内容一律写成未知项，不写成结论。
- 一次只澄清一个阻塞问题，避免「问十个、答一个」。
- 阻塞项按 `NEEDS_CLARIFY` 格式写，说明缺什么、影响谁、建议怎么补。
- 复述必须能被业务方用「对/不对」回答，不要写成开放式描述。
- 不限制为固定问题数量，也不为低影响细节反复打断人。可接受假设写依据与复查条件，仍未解决的阻塞项保留。

## 交接

产出 `understanding.md`，确认后进入 `write-prd`。未确认的理解不得直接写进 PRD 的范围或验收。
