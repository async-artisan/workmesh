### 启动链路与踩坑
- `apps/api/.env` 是必需项：`AppModule` 的 `ConfigModule.validate` 强制校验 `JWT_SECRET` / `JWT_REFRESH_SECRET`（≥32 字符、不能以 `replace-with-` 开头），缺失或直接复制 `.env.example` 都会启动即抛错。曾出现 `.env` 被覆盖回模板的情况，重启前先确认。
- **`DATABASE_URL` 必须显式带用户名**。`postgresql://localhost:5432/reqflow` 会让 Prisma 解析出空用户，报 `P1010 User '' was denied access`。正确：`postgresql://qiujianjun@localhost:5432/reqflow?schema=public`。
- 业务层**没有内存仓储**：auth / projects / requirements / knowledge / prd / trace 等 service 全部直接依赖 `PrismaService`。README 里"默认内存仓储"的说法与代码不符——只让 `/api/health` 起来不够，业务接口会 500，必须 `createdb reqflow` + `pnpm db:push`（22 张表）+ `pnpm db:seed`（1 组织 reqflow-demo、1 项目 DEMO）。
- **`nest start --watch` 在本机受控 shell 里不可靠**：文件变更后重启子进程时 `tree-kill` 抛 `spawn EBADF`（node v22 + tree-kill 1.2.2），整个 `pnpm dev` 随之退出（exit 1）。稳定替代路径：`pnpm exec tsc -p tsconfig.json && node dist/main.js` 起 API，`pnpm --filter @reqflow/web dev` 起前端（vite HMR 不重启子进程，不受影响）。
- `nest-cli.json` 的 `deleteOutDir: true` 会清 `dist`，在沙箱里可能触发 safe-delete 拦截；直接用 `tsc -p tsconfig.json` 覆盖输出可以绕开。

## 会话过期卡加载（22:50–23:20）

- 根因：`api/client.ts` 里刷新令牌用的也是同一个 `client`，refresh 返回 401 时再次进入响应拦截器，`refreshPromise` 已在等待中 → `await refreshPromise` 等的是自己 → 请求永不 settle，页面停在骨架屏且无错误提示。
- 修法：`/auth/login|register|refresh` 的 401 直接抛给调用方（不再进入刷新分支）；已 `_retry` 仍 401 或刷新失败 → `endSession()`（清 auth + 派发 `reqflow:session-expired`）。
- 外壳：App 监听该事件弹 toast「登录已过期，请重新登录」；`ToastHost` 在登录/注册页也渲染，否则跳转后提示随壳卸载消失。
- 回跳：未登录跳转带 `state.from`，Login 登录成功后回原路径（含 query）。
- 错误文案：拦截器统一用服务端 `message`（含 `{message:{message}}` 与字符串数组两种形状）覆盖 axios 默认英文，登录失败显示「邮箱或密码错误」。
- 补 CSS：`.toast-host/.toast/.icon-btn/.field-error/.chart-head/.trace-node.requirement` 之前根本没定义（toast 渲染成裸文本贴左边）。
- 测试：新增 `src/api/client.test.ts`（3 例：刷新被拒即结束会话、刷新成功重试、服务端文案覆盖）；web 11/11。
- 验证：伪造过期令牌进 /、/requirements、/prds 均在 270ms 内跳登录并出提示；有效 refreshToken 时留在原页且令牌已换新。

## 产品定位澄清（用户口述，重要：后续设计以此为准）

- 初衷**不是**在平台里集成 AI 对话。平台是产品/UI/前后端/测试/运维**各自带本地 AI（Codex、Claude Code、WorkBuddy…）协作的共同事实源**。
- 现实：每个人在自己电脑上用自己的 AI 干活；**页面不重要**，Web 只是大家看进度的视图；重点是本地 agent 与平台的上下文/证据双向流。
- 以**产品为源头**：产品维护整个项目知识库（易番番示例）；开发/测试/UI/运维各有自己的知识库，只在干自己活时用。内容留在本地，平台只存**事实 + 指针 + 挂靠关系**（联邦式，非单 repo）。
- 杀手锏是**变更传播**：产品改需求 → 平台知道哪些本地知识/commit/用例挂靠其上 → 主动通知受影响角色。
- 需要一套**统一规范**：同角色的多个人 + 各自的 AI 遵守同一套工作流规范，产出格式一致、可自动校验。规范要以文件形式下发到每个角色本地工作区（借鉴 spec-kit 的 constitution + 命令文件模式），而不是靠人自觉。
- 开源借鉴结论：spec-kit（Specify→Plan→Tasks→Implement，markdown 工件、38 agent 集成）、beads（git 版 JSONL 任务图、`bd ready`、--json、哈希 ID）、GitHub/GitLab（约定式追溯）。三者都只覆盖开发者单角色，**非开发者角色 + 跨角色追溯图 + 审批流是 ReqFlow 的空白位**。
- 已明确的重构方向：Knowledge 模块改「外部知识库注册表 + 条目挂靠需求」；TraceLink 增加「知识条目↔需求」边；CLI/MCP 升为一等公民，Web 降级为进度视图。

### 规范与重设计决策（2026-10-31 晚，用户拍板）

- 产出两份草案：`docs/collaboration-spec-v0.1.md`（协作规范）、`docs/redesign-v0.1.md`（数据模型 + 桥接器接口）。
- 编号：**必须带项目唯一标识** `YFF-REQ-123`，PROJECT_KEY 2–6 位大写、创建时定且不可变。
- 任务层：**要加**，编号 `YFF-REQ-123-T01`；commit 优先挂任务，向上聚合到需求；`reqflow ready` 返回任务而非需求。
- 知识库形态：**本地 Markdown + YAML front-matter + Git**（`.reqflow/knowledge/<role>/{index.md,log.md,index.jsonl,<topic>/*.md}`），依据 AGENTS.md/CLAUDE.md/SKILL.md/llms.txt、Google Open Knowledge Format、beads JSONL；Notion 等列为次选外部源，必须能导出 Markdown 才认可；agent 观察内容 ≠ 知识库事实，须人确认转 approved 才进上下文。
- 签字：**混合模式 C** —— 代码环节用 PR review 隐式代表（webhook 同步），其余环节平台内签字；agent 只能推到 `REVIEW_PENDING`，禁止自行置 DONE；签字不可撤销，靠追加反向记录更正。
- 桥接器命令面：`init/ready/context/deliver/sync/ack`，非交互 + JSON + 稳定 ID（抄 beads），同时暴露为 MCP 工具；context 包只给本地知识**指针**，正文由本地 agent 自读。

### 「重开 vs 改造」结论（用户问，我的建议）

- **建议改当前项目，走"减法式重构"**，不要新开仓库。
- 决定性理由：数据库从未真正写入过真实数据（迁移未应用到确认的库），**历史数据迁移成本≈0**，重开项目的唯一优势不存在，却要重付基建成本（auth/多租户/审计/CI/CLI 骨架/webhook）与 91.71% 覆盖率的测试。
- 另一理由：新项目容易复发旧病灶（"工程很满、验证是空的"），减法式重构强制面对"哪些真有用"。
- 处置划分：**保留**（monorepo/CI/门禁、auth 与 JWT、Organization/User/Project/ProjectMember、AuditLog、migration 流程与 db-check/db-plan、CLI 骨架、webhook 与 commit parser、部署脚本）；**删除**（AiRun/AiRunMessage/SSE/Runs 页面/平台侧 AiService 调用——旧"内置 AI"路线遗产）；**重写**（知识库模型改为只存索引的注册表、Web 页面改为进度视图、Requirement 状态机与编号、新增 Task/Artifact/SignOff/ChangeEvent）。
- embedding/RAG 管道可保留，但用途改为**平台内 PRD/工件检索**，不再承载角色知识正文。
