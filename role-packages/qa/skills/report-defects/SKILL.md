# 报告缺陷

## 何时用

- 评测失败且判定为产品缺陷。
- 修复后需要回归验证。

## 步骤

1. 复现：写最小步骤、前置状态、实际结果、期望结果。
2. 关联：需求编号、验收 key、任务编号、提交 SHA。
3. 定级：阻塞 / 严重 / 一般 / 建议，写清影响面。
4. 回传：交给对应开发任务，不直接改代码。
5. 回归：修复后按原用例复跑，记录结果。

## 规则

- 缺陷必须挂需求编号与验收 key；没有锚点的缺陷不可追踪。
- 不夹带需求变更：要改需求就走变更单，不写在缺陷里。
- 关闭需要回归证据，不接受「应该好了」。
- 一个缺陷一个根因；多个现象合并会让修复范围失控。

## 缺陷模板要点

| 字段        | 要求                   |
| ----------- | ---------------------- |
| 标题        | 现象 + 条件，一句话    |
| 前置        | 环境、数据、版本       |
| 步骤        | 可复现的最小步骤       |
| 期望 / 实际 | 引用验收 key 的原文    |
| 影响        | 阻塞哪些验收、哪些用户 |
| 证据        | 日志、截图、请求 ID    |

## 交接

产出 `defect.md`，回传开发任务。修复后回归通过，缺陷关闭；回归失败则重新打开并补充证据。
