# 运行保障

这份手册描述 API 进程在容器、反向代理或本地服务管理器中的最小运行约定。业务接口的完整协议仍以 [API 文档](api.md) 为准。

## 健康探针

- `GET /api/health` 是 liveness。它只确认 API 进程能处理 HTTP 请求，不访问 PostgreSQL；适合进程存活探针。
- `GET /api/health/ready` 是 readiness。它检查数据库连通性和迁移状态，成功返回 200，依赖不可用或 schema 未迁移时返回 503 `DEPENDENCY_UNAVAILABLE`。它不会因为依赖短暂抖动主动退出进程；编排器应据此暂时摘除流量。
- 两个端点都返回标准响应信封，并带 `X-Request-Id`。readiness 的未认证响应只返回枚举化原因，不回显连接串、主机名或驱动错误文本。

建议编排器将 liveness 与 readiness 分开配置：liveness 失败才重启进程，readiness 失败只摘除实例并等待恢复。部署脚本应在滚动更新时先等待新实例 readiness，再终止旧实例。

## 优雅停机

API 启动时注册 `SIGTERM` 和 `SIGINT` shutdown hooks。收到信号后，Nest 会停止接收新请求、等待 HTTP server 关闭，并调用模块的销毁钩子；当前实现会清理 Prisma 连接和 retention 定时器。容器的 `terminationGracePeriodSeconds` 应大于应用最慢的正常请求和数据库关闭耗时，生产环境还应让反向代理在终止期间停止转发新连接。

本地验证可以发送 `SIGTERM`，确认进程退出码为 0 且没有遗留 Node 进程；跨平台信号语义和真实负载下的最长排空时间仍应由部署环境单独演练。

## 日志与关联 ID

HTTP 错误日志使用 JSON 单行记录，至少包含 `event`、`method`、`path`、`status`、`code`、`message` 和 `requestId`。客户端可把错误响应中的 `error.requestId` 与服务端日志关联。日志不应包含密码、cookie、token、请求正文、连接串或完整上游响应。

启动失败使用 `event=api_bootstrap_failed` 的 JSON 记录并设置非零退出码。采集系统可按 `event`、`code` 和 `requestId` 建索引；不要把 `message` 当作稳定的机器解析字段，稳定筛选请使用 `event` 和 `code`。

## 进程内指标

`GET /api/metrics` 返回进程内累计快照，适合开发环境和轻量诊断：

- `requests`：已完成 HTTP 请求数；
- `failures`：处理链抛出异常的请求数；
- `activeRequests`：当前尚未完成的请求数；
- `statusCodes`：按 HTTP 状态码聚合的完成请求数；
- `averageDurationMs`、`p95DurationMs`、`p99DurationMs`：最近最多 1000 个请求的耗时统计（平均值使用全部累计请求）。

指标存储在单个进程内，重启后清零，未按路径、用户或项目分组，也没有持久化和多实例聚合语义。生产监控应在网关或 OpenTelemetry/Prometheus 采集层补充持久化、告警和跨实例聚合；不要把该端点当作完整的 Prometheus exposition 格式。

## 生产观测基线

正式部署至少应把以下信号送入部署方控制的日志、指标和告警系统，并保留来源实例、版本和环境标签：

- readiness 失败、迁移版本不一致、数据库连接池耗尽和进程重启；
- HTTP 5xx 比例、请求延迟的 p95/p99、活跃请求和限流拒绝；
- 登录失败、设备授权失败、凭据吊销、审批/发布失败和 webhook 验签失败；
- 备份成功/失败、备份年龄、恢复演练结果和磁盘剩余空间。

告警应链接到 [SECURITY.md](../SECURITY.md) 和本手册中的恢复步骤，避免只通知“服务不可用”而没有责任人、升级路径和回滚动作。生产环境不要把用户 token、Cookie、请求正文、数据库连接串或完整 GitHub 响应写入日志。

`GET /api/metrics` 没有认证且是进程内快照。公网部署必须由反向代理、网络策略或仅监听内部地址来限制访问；多副本部署应使用外部采集器按实例抓取或改造为具备明确聚合语义的指标，不要直接把多个实例的累计值相加。

## 备份与恢复演练

生产数据库至少应按部署方的恢复点目标（RPO）和恢复时间目标（RTO）设定备份周期、保留期限和加密密钥轮换。每次升级前应保留可识别的备份点，并先在隔离的新库恢复，再应用待发布迁移。

一次可审计的演练应记录：备份时间和来源版本、恢复目标、迁移版本、表/行数或业务摘要核对、恢复耗时、失败时的回滚步骤，以及谁批准恢复结果。恢复测试不得把备份直接覆盖唯一生产库，也不得把生产数据复制到公开 issue、日志或测试附件。

恢复完成后，应重新验证 `/api/health/ready`、登录、项目隔离、关键审批和备份任务；若票据加密密钥或 webhook 密钥缺失，必须按安全政策轮换或重新配置，而不是从日志中寻找秘密。

## 发布前检查

1. 迁移已应用，`/api/health/ready` 在目标数据库上返回 200。
2. 部署编排器分别配置 liveness 和 readiness，并验证 readiness 失败不会触发重启循环。
3. 以 SIGTERM 做一次排空演练，记录最长在途请求耗时和最终退出时间。
4. 日志采集器能解析 JSON 错误记录，并能用 `requestId` 从响应追到日志。
5. 指标采集明确标注“单进程累计”限制；多副本部署不得直接把不同实例的快照相加后当作精确时间序列。
6. 生产备份已在隔离新库恢复，核对结果、RPO/RTO、失败回滚和责任人已记录。
7. `/api/metrics` 的访问边界、日志脱敏和安全告警已由部署方审阅；默认 Compose 配置不得直接作为公网生产配置。
