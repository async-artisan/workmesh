# WorkMesh 社区入口

这里说明不同类型的参与者应该从哪里开始，以及哪些信息能让问题更快得到处理。项目当前仍是可自部署的开发版；文档、测试通过和生产支持分别需要不同证据，不能把其中一种当成另外两种。

## 我应该去哪里

| 目的                 | 入口                                                                                         | 提交时带上什么                                                 |
| -------------------- | -------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 报告可复现缺陷       | GitHub 的 Bug report 模板                                                                    | 版本或 commit、平台、最小复现步骤、预期与实际行为              |
| 提议功能或协议变化   | GitHub 的 Feature request 模板；大型变化先开讨论或设计 issue                                 | 用户问题、期望行为、替代方案、兼容性和迁移影响                 |
| 分享部署经验或提问   | [Feature request 模板](../../.github/ISSUE_TEMPLATE/feature.yml)（Discussions 待管理员启用） | 使用场景、运行时版本、已尝试的步骤和脱敏日志                   |
| 报告安全问题         | [安全政策](../../SECURITY.md)                                                                | 只走私密渠道；不要在公开 issue、PR、日志或截图中披露可利用细节 |
| 贡献代码、文档或测试 | [贡献指南](../../CONTRIBUTING.md)                                                            | 变更目的、验证命令、结果和仍未验证的边界                       |

提交前先搜索已有 issue。当前仓库的 Discussions 尚未启用；在管理员启用前，功能提案、部署经验和问题请使用 [Feature request 模板](../../.github/ISSUE_TEMPLATE/feature.yml) 或 [Bug report 模板](../../.github/ISSUE_TEMPLATE/bug.yml)。若问题只在本地环境出现，请同时阅读[支持矩阵](../support-matrix.md)；没有实测证据的平台只能作为社区报告，不能写成官方支持。

## 社区参与的最小规则

- 遵守[行为准则](../../CODE_OF_CONDUCT.md)，尊重不同经验和部署方式。
- 删除凭据、个人数据、客户数据和完整生产日志；公开链接应指向可供他人查看的最小证据。
- 将“源码中存在”“本机运行过”“CI 通过”“真实外部环境验证”分开描述。
- 讨论尚未确定的协议、架构或支持承诺时，写清楚这是提案，不是项目承诺。
