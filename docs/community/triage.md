# Issue 分流与处理口径

项目当前没有公开响应 SLA。本文用于让报告内容可复现、可排序，并让维护者在资源有限时保持一致判断。

## 报告者先做的检查

1. 搜索已有 issue 和[已知支持边界](../support-matrix.md)。Discussions 尚未启用；管理员启用后再把相关讨论作为补充入口。
2. 用最新受支持 Node/pnpm 组合重现；若无法升级，写明实际版本。
3. 记录最小步骤、预期、实际结果、错误 requestId（如有）和脱敏日志。
4. 数据库、迁移、备份或恢复问题必须说明目标环境是隔离库还是生产库；不要上传数据库 dump 或凭据。
5. 安全问题停止公开讨论，改按[安全政策](../../SECURITY.md)报告。

## 维护者分流顺序

维护者会先确认报告是否包含敏感信息和最小复现，再按以下维度排序：

- **安全影响**：凭据泄露、越权、数据损坏或可利用漏洞优先走私密响应流程。
- **数据与发布风险**：迁移失败、无法恢复、制品错误或阻断升级的问题优先于一般体验问题。
- **可复现性**：多个受支持环境可稳定复现的问题优先于仅单机且无法复现的问题。
- **用户范围**：影响默认路径、安装或核心交付闭环的问题优先于边缘功能。
- **证据质量**：有最小复现、失败 CI 或可运行样例的问题更容易进入实现排期。

维护者可能请求补充信息、标记为待复现、合并重复报告、转为讨论或关闭超出当前支持范围的问题。关闭不代表问题没有价值；若补充了新环境、复现步骤或修复方案，可以重新打开相关讨论或提交新 issue。

## 提案进入实现前

涉及 API、数据库、认证、证据门禁、角色包协议或部署方式的提案，应先说明用户问题、替代方案、兼容性、迁移、回滚和验收条件。维护者接受提案讨论不等于承诺实现、发布日期或支持 SLA。
