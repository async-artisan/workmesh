# WorkMesh 角色工作流规范 v0.1（草案）

> 配套《协作规范 v0.1》。本文定义**每个角色各自的完整工作流**，以及**角色之间的协同协议**。
> 无论使用何种 agent 工具（Claude Code / Codex / WorkBuddy / 其他），都必须遵守本文。
> 状态：草案，待评审。

---

## 0. 通用骨架（所有角色共用）

任何角色、任何 agent，接手一项工作时都按同一骨架执行：

```
① 取活      workmesh claim --task <taskId>  → 拿到本角色可执行的任务
② 取上下文  workmesh context <需求编号>      → 拿到权威上下文包（禁止凭记忆臆测）
③ 生产      按本角色阶段推进
④ 自检      逐条过 DoD 清单（缺一不得交付）
⑤ 交付      workmesh deliver                → 工件带锚点，本地先过 schema 校验
⑥ 提交签字  置为 REVIEW_PENDING            → 禁止自行置 DONE
⑦ 交接      签字通过 → 解锁下游角色的任务
```

**通用禁令**（所有角色，详见协作规范 §8）

- 不臆造需求：产品源中不存在的内容不得产出
- 不改验收标准：有异议走 `NEEDS_CLARIFY` 回问，不自行修改
- 不越权：不修改其他角色的工件
- 不省略锚点：任何产出必须携带需求编号
- 不自行宣告完成：完成与否由签字决定

## 1. 产品（PRODUCT）——源头

**触发**：业务诉求、用户反馈、迭代规划；或收到下游 `NEEDS_CLARIFY`

| 阶段            | 动作                           | 产出              |
| --------------- | ------------------------------ | ----------------- |
| P1 收集与澄清   | 收集诉求，标注来源与背景       | 需求条目（DRAFT） |
| P2 撰写 PRD     | 写清目标、范围、用户故事、边界 | `prd.md`          |
| P3 定义验收标准 | 每条标准可测、可判定           | PRD 中的验收章节  |
| P4 评审定稿     | 提交评审，通过后定稿           | 定稿版本 + 签字   |
| P5 拆解任务     | 按角色拆出任务，指定依赖       | `Task` 列表       |
| P6 变更管理     | 需求变更必须升版本并触发传播   | `ChangeEvent`     |

**DoD 自检**

- [ ] 每条验收标准可测且有明确判定方式
- [ ] 范围与边界已写清（做什么、不做什么）
- [ ] 任务已拆分，且每个任务归属明确角色
- [ ] 存在外部依赖（设计/接口/数据）的已在 PRD 中标注

**交接**：定稿并签字 → 状态 `PRD_READY` → 解锁 UI 与前后端的任务。
**协同**：收到下游 `NEEDS_CLARIFY` 必须在任务上回应；若是实质修改，升 PRD 版本并触发变更传播。

## 2. UI（UI）

**触发**：需求进入 `PRD_READY`，且存在 UI 任务

| 阶段        | 动作                             | 产出                       |
| ----------- | -------------------------------- | -------------------------- |
| U1 理解     | 读 PRD + 现有设计规范            | —                          |
| U2 设计     | 出页面、状态、交互               | 设计文件（命名含需求编号） |
| U3 标注约束 | 标出边界条件、异常态、响应式要求 | `design.md`                |
| U4 自审     | 对照验收标准逐条检查覆盖         | 自审结果                   |
| U5 确认     | 提交产品 + 设计负责人确认        | 签字                       |

**DoD 自检**

- [ ] 每条验收标准都有对应界面表现
- [ ] 覆盖正常态、空态、错误态、加载态、权限受限态
- [ ] 文件命名与 front-matter 均含需求编号
- [ ] 与既有设计规范一致，偏离处已说明理由

**交接**：确认 → `DESIGN_READY` → 解锁前后端任务。
**协同**：PRD 信息不足以完成设计时，发 `NEEDS_CLARIFY` 给产品，不自行假设。

## 3. 前端（FRONTEND）

**触发**：`DESIGN_READY`（有设计依赖）或 `PRD_READY`（纯逻辑改动）；且任务无阻塞

| 阶段        | 动作                               | 产出                       |
| ----------- | ---------------------------------- | -------------------------- |
| F1 取上下文 | `ready` + `context`                | —                          |
| F2 方案     | 说明改动范围、受影响组件、接口依赖 | 实现方案（写在 `impl.md`） |
| F3 编码     | 分支/commit 带需求与任务编号       | 代码                       |
| F4 自测     | 按验收标准逐条自验                 | 自测记录                   |
| F5 回交     | `deliver` + 提交 PR                | `impl.md` + PR             |
| F6 评审     | 等 PR review                       | 签字（PR 隐式）            |

**DoD 自检**

- [ ] 每条验收标准都有对应实现或明确的未完成说明
- [ ] commit/PR 含 `YFF-REQ-123-T01` 形式编号
- [ ] 受影响组件/接口已在 `impl.md` 列出
- [ ] 遗留项与已知限制已写明（不隐藏）

**交接**：PR review 通过 → 任务 `DONE` → 关联任务全部完成后需求 `CODE_LINKED`。
**协同**：实现与 PRD 冲突时发 `NEEDS_CLARIFY`，**不得自行变更验收标准**。

---

## 4. 后端（BACKEND）

**触发**：同前端；通常无设计依赖，可更早开始

| 阶段        | 动作                               | 产出            |
| ----------- | ---------------------------------- | --------------- |
| B1 取上下文 | `ready` + `context`                | —               |
| B2 方案     | 接口设计、数据模型变更、兼容性影响 | 实现方案        |
| B3 编码     | 分支/commit 带编号                 | 代码            |
| B4 自测     | 接口自测 + 边界用例                | 自测记录        |
| B5 回交     | `deliver` + PR                     | `impl.md` + PR  |
| B6 评审     | 等 PR review                       | 签字（PR 隐式） |

**DoD 自检**

- [ ] 接口契约明确（入参、出参、错误码）
- [ ] 数据变更有迁移方案且可回滚
- [ ] 向后兼容性影响已评估
- [ ] 性能与权限约束已考虑并写明
- [ ] commit/PR 含编号

**交接与协同**：同前端。

## 5. 测试（QA）

**触发**：需求 `CODE_LINKED`

| 阶段        | 动作                             | 产出              |
| ----------- | -------------------------------- | ----------------- |
| Q1 取上下文 | 读 PRD 验收标准 + 已回链代码范围 | —                 |
| Q2 设计用例 | 覆盖验收标准、边界、异常、回归   | `cases.yaml`      |
| Q3 评审用例 | 用例评审（平台内）               | 签字              |
| Q4 执行     | 执行并记录结果                   | 执行结果          |
| Q5 缺陷管理 | 缺陷挂需求编号并回传开发         | 缺陷条目          |
| Q6 回写     | 结果回写需求                     | `cases.yaml` 更新 |

**DoD 自检**

- [ ] 每条验收标准至少一个用例
- [ ] 覆盖边界与异常，不只有happy path
- [ ] 用例 ID 为 `TC-YFF-REQ-123-<序号>`
- [ ] 缺陷全部挂需求编号，无孤立缺陷
- [ ] 遗留风险已写明

**交接**：结果确认 → `TESTED` → 解锁运维任务。
**协同**：发现需求描述歧义发 `NEEDS_CLARIFY`；发现代码问题回传对应任务，**不直接改代码**。

## 6. 运维（OPS）

**触发**：需求 `TESTED`

| 阶段        | 动作                         | 产出         |
| ----------- | ---------------------------- | ------------ |
| O1 发布准备 | 确认依赖、灰度策略、回滚方案 | 发布计划     |
| O2 发布     | 执行发布                     | 发布记录     |
| O3 冒烟     | 按验收标准做生产冒烟         | 冒烟结果     |
| O4 记录     | 版本号、时间、环境、影响需求 | `release.md` |
| O5 确认     | 发布确认                     | 签字         |

**DoD 自检**

- [ ] 回滚方案存在且已验证可行
- [ ] `release.md` 含影响需求编号列表
- [ ] 冒烟覆盖该需求的关键路径
- [ ] 监控与告警已就位

**交接**：确认 → `RELEASED`，需求闭环。

## 7. 角色协同协议

### 7.1 交接触发

交接**不靠通知，靠状态门**：上游签字通过 → 需求状态推进 → 下游角色的任务自动出现在其可领取队列中（`workmesh claim --task <taskId>`）。任何"口头说做完了"都不产生交接效力。

### 7.2 回问机制（NEEDS_CLARIFY）

任何角色发现上游信息不足、矛盾或错误时：

```
NEEDS_CLARIFY
  需求编号：YFF-REQ-123
  任务编号：YFF-REQ-123-T03
  依据缺口：PRD 未定义"无 key 时"的降级行为
  影响：阻塞本任务，无法判断验收口径
  建议：请产品补充该分支的预期表现
```

- 回问写入平台并通知上游角色任务；
- 上游必须回应：补充信息（升版本）或裁定口径；
- 回问期间任务标 `BLOCKED`，不计入个人停滞。

### 7.3 变更传播

产品更新需求并定稿 → 生成 `ChangeEvent` → 按挂靠关系定位受影响的知识条目、任务、工件、用例 → 推送给对应角色 → 各角色确认或更新后 `ack`。**未 ack 的变更在进度视图上持续暴露。**

### 7.4 同角色多人并行

- 任务需**认领**（`ready` → `IN_PROGRESS`）后才可开工，避免重复劳动；
- 同角色多人的 agent 各自拉动不同任务，依赖 `blocked-by` 保证顺序；
- 本地知识条目使用稳定 ID（路径哈希），避免多机并发冲突。

### 7.5 裁剪规则

小型需求可裁剪角色（如纯文案改动无需 UI、无需测试），但必须：

1. 在需求中显式声明跳过哪些角色及理由；
2. 状态机按剩余环节推进，被跳过的门自动放行；
3. 裁剪记录进审计，事后可追溯"为什么这条没测"。

### 7.6 协同禁令

- 不越权修改他人工件（前端不改用例，测试不改 PRD，开发不改验收标准）
- 不私下绕过状态门（未签字不得进入下一环节）
- 不重复造事实（所有依据来自上下文包，不来自聊天记录或个人记忆）

---

## 8. 规范的落地方式

- 本文与《协作规范》随 `.workmesh/` 下发到每个角色的本地工作区；
- `workmesh roles install --package <dir> --project <uuid> --host <host>` 写入该角色目录，并写入 agent 入口文件（AGENTS.md / slash command）；
- 每个角色的 agent 每次开工自动加载本角色的 SOP；
- 平台对工件做 schema 校验，不合格拒收——规范因此是硬约束而非建议。
