**目标：** 各角色在自己的本地 AI 中使用各自工作流，通过 WorkMesh 共同管理知识发布、需求基线、任务、交付、人工审批与交接。首版跑通产品本地候选→Web发布→下游确定版本→交付／返工→GitHub代码证据→发布验收。

**架构：** 模块化单体 NestJS API、React 人工 Web、TypeScript CLI、PostgreSQL。Redis可选，不承担唯一事实。CLI与未来MCP是薄连接层，不把所有角色的本地步骤搬成中心执行引擎，也不绑定易番番、某个目录或某个AI工具。

## 2. 本次已固定的技术选择

- **协议：** API `/api/v1`、bridge `1.0`；成功和错误envelope固定。角色用动态ProjectRole ID，初始六角色只是数据，不作为不可扩展全局enum。一个项目绑定多个仓库。
- **身份：** Web使用服务端opaque HttpOnly cookie与CSRF／Origin检查；CLI浏览器授权只取得受限AgentCredential，不保存HUMAN access/refresh JWT。发布和批准只由Web准确版本二验完成。
- **知识：** 复用平台正文库，文档身份与不可变revision分离；本地approved仅为声明。KB级授权覆盖正文、标题、索引和快照，草稿不替代发布版。默认无外部模型依赖或外发。
- **协作：** 工作流定义、实例、任务、认领和本地步骤分别管理。认领持续保留并显式释放；输入版本和执行generation不同，过期claim不能交付。
- **验收：** 理解、PRD发布、知识发布、任务接受、release接受分别建立ReviewRequest。每个slot绑定有权的人与具体产物；ALL最后批准与发布／状态更新同事务，不再单独保留旧签字旁路。
- **可靠性：** 所有关键数据库动作按02的锁与Serializable规则执行，最多三次纯DB重试；业务幂等保存结果，网络或副作用不在事务重试中重复执行。CodeReviewEvidence先prepare，再绑定preview与票据，不能最终批准时偷换证据。
- **本地集成：** 默认角色包、项目版本化定制和个人advisory分层；首版声明支持Codex／Claude Code的规范入口，但需实测对应版本，不承诺所有工具自动遵循。CLI发行包含资源，macOS／Linux明确选择user-only file store，Windows不在首版支持范围。
- **代码托管：** 核心只消费标准证据，GitHub.com是首个具体实现；IMPL仍要求他人针对当前交付提交的有效评审及合并。Codeup能力核验单列，不根据PASS或GitLab外形猜测支持。
- **迁移：** 新 `workmesh_v1` schema与旧数据隔离，新API不兼容旧旁路；旧记录保留，候选重新评审，缺依据的旧批准不升级成有效签字。迁移／重建真实库仍需单独确认。

这些是本技术方案选定的实施规则，不表示它们已经通过运行验证。已确认的产品边界保持不变；限定首个交付范围，不省略该范围必需的权限、版本和故障处理。

## 3. 实施路径与第一个可用成果

1. **T00–T02，契约、schema和身份：** 冻结共享DTO与scope，创建隔离目标模型，实现Web／Agent身份及当前权限，先封住可冒报身份和直接改状态的路径。
2. **T03，第一条服务端纵向切片：** 用真实HTTP和隔离数据库验证受限主体提交理解／PRD候选、HUMAN会话独立确认发布、下游读取同一修订正文；此时不宣称完整CLI／Web或任务交付已经完成。不能要求产品先已有定稿PRD才能开始理解需求。
3. **T04–T06，可靠交付与工具接入：** 分别完善claim、ArtifactSet、Review、ChangeInbox、GitHub适配、CLI角色包与两宿主入口；同文件由一位执行者串行集成。
4. **T07–T08，完整联调与交付：** 复用现有Web页面完成准确slot操作，跑隔离数据库与浏览器闭环，执行受控迁移和恢复演练，发行CLI包内容检查。
5. **T09，Codeup：** 在实际企业形态和授权测试仓验证能力后实现适配器；不阻碍通用核心与GitHub开发，但不把Codeup未验证部分标为支持。

第一个服务端成果不是新建完一批表，而是候选、平台发布和下游读取在真实HTTP和隔离数据库中成立；完整用户成果还必须在T06/T07用打包CLI与浏览器复现，并接上T04快照和任务交付。方案不要求所有角色先实现同样复杂的完整本地工具，角色包可逐项验收，但平台门禁保持一致。

## 4. 开发必须保留的边界

- 当前工作区已有大量未提交功能及改名变更，实施前逐项记录并保留，不能reset／stash后从旧版本重做；提交、推送和外部发送另行按授权执行。
- 新schema、迁移脚本、API与Web是未来实现任务；本轮不运行这些操作。没有明确环境身份时不访问数据库，不启动或重启服务。
- 单元与fixture、真实Nest HTTP、隔离PostgreSQL并发、dist打包、浏览器人工确认、真实GitHub及Codeup分别给证据，不相互冒充。
- 未读取真实秘密配置，故部署实例、备份位置、外部测试仓与组织授权需执行时确认；这不要求开发者重新决定API、schema或门禁语义。
- 暂不实现MCP server、自动租约／执行、全角色中央工作流引擎、GitLab审批、实时多人编辑或强行引入专用向量设施。默认不上传个人聊天、私人记忆或客户资料。

## 5. 开发就绪与验收标准

完成01–05的结构化文档校验和跨册接口一致性复核后，可以按06从T00开始实施。关键产品与技术语义不再留给执行者临时猜测；具体代码组织可以在既有模块边界内保持最小实现。

“实施完成”的标准另见06：权限、版本、并发、失效传播、输入正文获取、故障恢复和用户可见交接都须有新鲜证据。没有真实外部平台授权时可完成本地契约与模拟层，但该平台联调状态必须明确未验证。

本次交付是技术实施方案，不是源码、migration、服务、数据库或外部集成已完成的声明。
