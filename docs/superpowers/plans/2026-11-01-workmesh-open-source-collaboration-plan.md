# WorkMesh 协作事实与共享知识改造计划

日期：2026-11-01。状态：计划修订并落盘，尚未实施。本文整合对话中确认的完整计划，明确各角色本地 AI 工作流与 WorkMesh 的集成边界，以及厂商中立的代码托管设计；现有实现不因此获得新的角色、工具或平台支持，也不因此取得开源发布资格。

本文保留为产品与架构总纲。开发使用配套[技术实施方案 v1](2026-11-01-workmesh-technical-implementation.md)，其中01–06分册进一步固定模型、权限、API、流程schema、迁移与任务验收；不得把本总纲的能力描述当作当前实现或跳过技术契约。

## 1. 目标与已确认决策

**目标：** 将当前原型改造成连接各角色本地 AI 工作流的协作底座，提供可信身份、共享正文、确定版本上下文、可靠交付和人工门禁。开源用户可私有部署，不要求统一 AI 客户端，也不要求将公司项目代码、知识或凭据搬到 GitHub。

**架构：** 保留 TypeScript、NestJS、React、Prisma、PostgreSQL 与模块化单体。各角色在本地 AI 中运行自己的工作流，CLI 和后续可选 MCP 作为薄桥；服务端管理正式事实、权限、交接与批准，而不是统一远程执行角色的全部步骤。GitHub、云效 Codeup 等代码托管平台由独立适配器接入；不引入微服务、Kubernetes、Temporal、Kafka 或完整 Backstage。

| 项目           | 已确认的执行边界                                                                                                      |
| -------------- | --------------------------------------------------------------------------------------------------------------------- |
| 本地角色工作流 | 产品、UI、前后端、测试、运维分别拥有工作流，通过统一契约集成 WorkMesh；不是把产品工作流迁成所有角色共用的中心执行器。 |
| 工具适配       | 流程内容与工具入口分离，可集成已有本地实现；默认工作流包不强制用户更换 AI 工具或本地实现语言。                        |
| 共享知识       | WorkMesh 托管团队知识发布版；本地负责编辑与版本副本，个人记忆不自动上传。                                             |
| 知识权限       | 按知识库授权；默认项目共享，受限库限定成员或角色，维护角色不等于读取权限。                                            |
| 人工审批       | Web 独立确认；同一人可兼任多个业务角色，每个角色的决定独立记录。                                                      |
| 代码门禁       | 必须具备针对被验收提交的有效他人评审与合并证据；不允许作者自审冒充外部评审。                                          |
| 代码托管       | 核心厂商中立，先交付 GitHub 适配器；Codeup 为明确的后续接入阶段，不当作 GitLab 兼容入口。                             |
| 任务接管       | 持久认领，责任人或管理员显式释放，不自动超时接管或重跑外部动作。                                                      |
| 知识外发       | 默认禁止；项目管理员显式批准指定提供商后，应用管理的模型处理才允许外发。                                              |
| 兼容           | 开发阶段直接统一新设计，不保留旧接口、旧配置或旧门禁兼容层；未授权删除现有数据。                                      |

### 1.1 通用产品与项目边界

- WorkMesh 是项目协作底座，不将产品目标收缩为需求 CRUD、AI 聊天界面或统一远程 Agent 执行平台。
- 一个逻辑项目可以关联多个代码仓库和知识来源。项目、仓库、角色、人员和 AI 工具分别建模，不以一个目录、一个仓库或一个 Agent 代替整个业务项目。
- 易番番、nzERP、客户询价单及 chanpingzhishiku 只用于检验实际场景；通用模型、模板和安装流程不依赖它们的业务结构、本机路径或特定角色划分。
- 保持 WorkMesh／workmesh／@workmesh/* 命名和独立 Git 仓库归属；项目登记与安装不得将其重新纳入父仓库管理。实际部署位置由使用者配置，不要求本工作区目录结构。

### 1.2 技术与复杂度边界

当前优先解决权限、版本、一致性、交接和恢复，不为这些问题更换语言或套用重型基础设施。Redis 不是核心流程的必需依赖，不承担唯一的任务认领、发布事实或批准记录；未配置或不可用时，核心知识读取、发布、任务和审批依靠 PostgreSQL 仍可工作，缓存增强按需降级。性能和容量判断使用实际基准，不把框架选择当成性能证明。

完整性以已声明范围的正确性和可验证性衡量：权限、版本、错误处理及必要验收不能以“先做简单版”为由省略；可推迟的是尚无需求依据的编辑器、基础设施和自动化，而不是已经承诺的协作保证。

产品路径先完成本地检索、理解、澄清、PRD 草稿与评审，再发布需求基线；经明确授权的共享内容通过 WorkMesh 保存，而不是只留在个人聊天中。研发、测试等角色从自己的输入与工作流起步，不重复走一遍产品全过程。

共同协作闭环：发布需求与知识 → 认领任务 → 获取确定版本上下文与角色工作流 → 本地生产 → 幂等交付 → Web 人工确认 → 门禁推进 → 上游变更后重新检查。

本计划借鉴稳定身份、版本化批准、条件更新、幂等与事务事件、输入锁定、正式 CLI/API 契约，不把安装参考项目本身作为目标。GitHub、Codeup 的厂商状态只由对应适配器解释，不能进入核心规则形成分支。

## 2. 本地角色工作流集成与开源经验

### 2.1 借鉴机制，不整套替换现有工作方式

| 参考对象          | 已核对的设计经验                                                      | 在本计划中的应用                                                                   | 不作为保证的能力                                                              |
| ----------------- | --------------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Spec Kit          | 流程、模板定制和 Agent integration 分离；同一过程可适配不同工具入口。 | 角色流程保留单一来源，按所选工具生成入口；流程包与工具适配分别版本化。             | 本地 gate 不是经过业务身份认证的批准，不把其执行器搬到 WorkMesh 服务端。      |
| BMAD              | 专业角色使用不同工作方式，以需求、设计、架构和验证产物接力。          | 产品、研发与测试各有本地 SOP，交接共享工件而非整段聊天；角色和步骤按任务需要参与。 | 角色 persona 不证明专业结论正确，也不强制所有任务串行经过所有角色。           |
| OpenSpec          | 以 schema 描述产物、模板、指导与依赖，围绕变更组织可继续修改的资料。  | 明确角色输入、输出和前置依赖；本地支持评审返修，平台接收准确版本与验证证据。       | 文件存在、任务打勾或本地 archive 不等于平台评审、发布或验收通过。             |
| Agent Skills      | SKILL.md 与按需加载的 references、assets、scripts 共同封装能力。      | 工作流包携带 SOP、模板、检查表和辅助资源，按宿主支持生成 skill、命令或规范指针。   | 安装不保证触发或遵循，allowed-tools 等元数据不能授予 WorkMesh 权限。          |
| MCP 与 GitHub CLI | 本地客户端通过明确的数据、动作和机器输出契约访问中心。                | CLI 保持一等入口；后续 MCP 与 Web 使用同一授权和业务服务，不重复实现状态机。       | MCP 不是角色执行器或人工审批系统；GitHub CLI 开源不等于 GitHub 服务整体开源。 |

以上是方法和协议参考，不要求同时安装这些框架，也不新增工作流市场。Spec Kit、OpenSpec 等工具仍在快速演进；BMAD 的稳定与预览资料也应分开。实际采用时固定发行版及支持的宿主环境，复用代码前检查许可，不从动态文档推断所有版本均可用。

### 2.2 三层职责与状态归属

| 层次                 | 负责的事情                                                                 | 权威边界                                                                           |
| -------------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 本地角色工作流       | 检索、理解、提问、编辑、编码、自测、意见处理、局部续跑。                   | 可以记录临时思路、草稿及详细进度，不能自行认定团队正式发布、验收或批准已成立。     |
| CLI／后续 MCP 连接层 | 解析工作区和凭据，获取知识与任务，提交候选或工件，查询意见和当前状态。     | 只连接同一业务契约；工具名称、提示词、本地勾选不能越过服务端权限。                 |
| WorkMesh 协作底座    | 共享需求和决定、发布版本、任务归属、正式工件、审批结果、跨角色交接和变更。 | 正式共享状态由平台确认；在授权范围内返回版本、证据和阻塞原因，不执行任意本地脚本。 |

本地工作流可以保留自身阶段，不必将每次对话和内部步骤映射为平台状态。正式共享检查点必须关联平台需求或任务、操作者、产物版本和所用工作流版本；本地运行标识只是关联执行记录，不能形成第二份正式需求或批准权威。

需要共享的确认决定、候选理解、评审意见和产物按明确授权登记到平台；未授权的聊天、私人记忆、源资料和凭据不自动同步。候选理解仍是候选，用户理解确认、PRD 业务批准、代码评审和最终验收不得互相替代。

### 2.3 角色工作流包与工具入口

- 每个包声明稳定标识、版本、适用角色、输入输出契约及支持的桥接协议；SOP、模板、自检规则和必要资源统一维护，不在各工具入口复制不同版本。
- 工作区只配置实际需要的角色及工具适配。安装或更新不得覆盖用户无关规范和本地草稿，也不从资料正文获取安装、脚本执行或提权授权。
- 同一项目的正式验收要求由平台和项目规范决定。个人可调整本地工作方法，但不能通过覆盖提示词降低安全、发布、代码评审或验收门槛。
- 任务执行包记录角色工作流与项目规范版本；升级不静默改变进行中的任务。版本不兼容时给出明确诊断并阻止不安全写入，不能猜测旧结果仍满足新要求。
- 包内辅助脚本仅在本地、明确授权和宿主权限范围内执行；固定可信来源与版本，不因包安装就自动执行脚本或授予平台能力。

首版复用现有规范下发能力并补齐角色包、工具入口和桥接约定，不先建设通用流程 DSL、中心命令调度或远程 Agent 集群。

### 2.4 产品工作流集成样例与其他角色

`chanpingzhishiku` 用于验证产品本地工作流如何接入，不是 WorkMesh 的项目模型或内置业务数据。可以保留原有本地实现，通过适配层连接平台；不要求把 Python CLI、SQLite、本地目录或所有内部状态迁到 WorkMesh 中央运行。

产品工作流应保留：意图路由与检索核验、事实／假设／未知项、有依赖的澄清队列、答复落实到规则和验收条件、理解确认、PRD 草稿、评审修改任务及返修恢复。模板章数、逐题交互和原型步骤属于产品侧规则，不成为所有角色的通用必经阶段；理解确认也不自动授权原型或代码实现。

前后端围绕契约、实现、自测和代码评审组织本地流程；UI 围绕设计及状态覆盖；测试围绕用例、执行与回归；运维围绕发布、冒烟和回滚验证。它们共享平台输入、工件引用与交接规则，不共享一条固定产品流水线。

先用产品工作流与下游研发交接验证集成契约，再逐角色完善默认包及宿主验收。未完成实际验证的角色或工具只标注设计支持范围，不能宣传为已可用。原仓库的业务原文、历史决定及客户资料仍是项目资产，不随通用流程包公开。

### 2.5 接入闭环与失败边界

1. 本地 AI 按角色工作流开始，区分讨论、候选出稿、共享登记和正式批准；不把每次聊天强制变成平台任务。
2. 获得相应授权后取得或登记需求／任务，绑定工作流版本、项目规范和已授权输入；准备不足时明确缺口，不从旧聊天补造事实。
3. 本地生产和自检后提交准确产物版本、检查来源与必要的决定落点；自检结果是提交方证据，不冒充独立验证。
4. 平台按统一契约接收、校验和组织评审；本地等待或读取实际批准、返修、阻塞结果，再继续自己的下一步，不能用本地 approve 代签。
5. 网络中断时保留草稿和可恢复的本地进度，查询平台并安全重试共享检查点；不把超时当成成功或失败已确定，也不重复产生正式工件。

“已取得输入”“已向 Agent／模型提供输入”“产物满足要求”是不同证据。技能触发、本地步骤结束、产物文件存在均不能替代 WorkMesh 的授权批准及业务验收。

### 2.6 分层自定义与流程实例

工作流采用“默认角色包 → 项目版本化定制 → 个人非强制性偏好”的定制层次；平台安全和授权底线始终保留，不作为可覆盖配置。

- 默认角色包提供可复用的步骤、模板、自检方法和输入输出约定。项目可以在平台开放范围内配置步骤路径、参与角色、任务依赖、交接对象和必要评审；裁剪必须显式说明理由并经有权负责人确认，不能降低既定的代码他人评审或人工批准要求。
- 项目负责人发布流程配置，专业负责人维护角色 SOP；Agent 可以提交修改建议，不能自行把流程或验收口径改成正式版本。个人可调整工具、交互偏好及非强制本地步骤，不能覆盖项目交付要求。
- 模板描述规则，实例落实本次需求的责任人、输入基线、必需产物、验收条件和下一接手人。任务按实际依赖并行或串行，测试可以提前参与需求与用例评审，不固定为六角色单线流水线。
- 交接必须说明产物及其版本、验证证据、接收责任和未决项。澄清记录缺失依据、业务影响、回答责任人及恢复条件；返工回到相应任务和责任人，不因一句“做完了”自动交接。
- 阶段、工作状态和版本有效性分别表达。暂停、阻塞、返修或撤回不得抹去已发生的业务阶段和历史决定，也不得被计作完成；恢复时先核对当前基线、权限和未决事项。
- 项目定制发布后形成新版本；新任务采用选定版本，在途实例固定原有版本。确需升级时显式记录影响和版本切换，重新检查产物及门禁，不静默换规则。输入输出不兼容时拒绝错误交接，而非猜测字段或丢弃要求。

首版采用角色包与结构化项目配置，不建设拖拽流程编辑器、通用脚本执行器或任意远程步骤调度。自定义规则必须经过结构、依赖和授权边界校验；能表达某个步骤，不代表获得执行该动作的权限。

## 3. 代码托管中立设计

### 3.1 分清核心、厂商适配和部署配置

- **领域核心：** 只判断仓库归属、需求与任务关联、被验收提交、有效的人类评审、合并事实和证据有效性，不直接判断 GitHub 的 `APPROVED` 或 Codeup 的 `PASS` 字符串。
- **适配器：** 负责本厂商的鉴权、事件校验、API 查询、分页、字段解释与规范化证据。首个具体实现为 GitHub；Codeup 不经由 GitLab 适配器转接。
- **连接配置：** 保存受控的代码托管连接与仓库映射，支持项目选择连接。凭据通过部署秘密管理或受控秘密引用提供，不写入正文、URL、客户端输出或仓库。
- **项目隔离：** 连接与仓库绑定必须校验组织及项目权限，不因编号、仓库名称相同或用户提交 URL 就跨项目复用证据。

只建立服务内有限接口与显式注册表，不建设远程插件市场、动态加载框架或万能适配 DSL。

### 3.2 仓库与合并请求身份

仓库使用厂商、服务实例、组织或命名空间、厂商仓库 ID 形成完整引用；合并请求使用该仓库引用与厂商请求 ID 标识。ID 按厂商契约保存，不假定全是整数。

仓库 URL 是展示、导航或克隆地址，不是唯一的业务身份。不同企业、服务实例中的同名仓库和同号合并请求不得合并；接收事件中的仓库也必须与已配置连接匹配。

项目与仓库采用明确的一对多关联；任务和代码证据引用实际涉及的仓库，不能继续用项目上的单个 repositoryUrl 代表全部代码范围。跨仓库交付需列明各仓库版本与证据，未验证的仓库不能被其他仓库的通过结果覆盖。

核心允许保留现有内部 `PullRequest` 命名，但公共契约与页面使用“合并请求／代码评审”概念，不能要求用户在 GitHub 上创建对象才能工作。

### 3.3 适配器契约与能力声明

每个适配器至少明确以下职责；没有实现的能力必须明确返回不支持或未知，不能构造成功证据：

| 能力               | 输出及约束                                                                                             |
| ------------------ | ------------------------------------------------------------------------------------------------------ |
| 验证并解析事件     | 校验对应连接的请求认证、仓库身份与事件类型，转换为内部事件；不得以“缺少 GitHub 头”默认视为另一个厂商。 |
| 查询合并请求       | 得到来源提交或源版本、作者、合并状态及可用的合并提交信息，不将合并提交冒充评审提交。                   |
| 查询当前评审       | 保留评审者稳定 ID、决定、来源记录标识和可证明的版本关联；原始状态与规范化结论分开记录。                |
| 核验指定提交的批准 | 返回有效、无效、证据不足或能力不支持，以及原因和核验时间；只有有效结论可参与代码放行。                 |
| 对账与补偿         | 使用实际支持的分页或游标重新核验，处理漏通知、重复和乱序；不承诺厂商未提供的历史回放或增量保证。       |

统一代码评审证据包含仓库引用、合并请求引用、作者、被验收提交、评审者、决定与版本关联依据、合并事实、核验时间和厂商证据引用。只传 `provider + number` 或仅传评审通过状态，不能作为完整批准依据。

能力不足不能降低门禁。Webhook 只能触发同步，不能单凭一条“通过”通知永久批准某个请求；签字前核验当前证据，核验后发生的新撤销或版本变化继续触发有效性重算。跨系统不能保证绝对同一时刻原子快照，应记录核验时间与证据并明确边界。

### 3.4 Codeup 已核实能力与尚未成立的保证

2026-11-01 已读取云效官方新版资料，确认存在合并请求查询、版本列表和 Codeup 专用 Webhook；未连接公司的组织、代码库或账号。

| 官方能力                   | 接入时可以据此设计什么                                                              | 不能据此声称什么                                                                         |
| -------------------------- | ----------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| GetChangeRequest           | 查询评审人、评审意见、时间、请求状态和已合并版本。                                  | 评审条目本身没有明确的 review SHA／PatchSet 绑定，不能仅凭评审时间证明批准针对当前提交。 |
| ListChangeRequestPatchSets | 用 `commitId`、版本 ID 和源／目标类型识别源版本。                                   | 版本可查不等于该版本的批准也已被证明。                                                   |
| Codeup Webhook             | 按 `Codeup-Event` 路由，校验该连接配置的 `X-Codeup-Token`；无认证配置的事件不接收。 | 不假定存在 GitHub 式 HMAC、可靠唯一事件 ID、自动重试或明确的撤销评审事件。               |
| ListChangeRequests         | 分页查询、按更新时间排序，设计轮询对账。                                            | 不假定存在更新时间过滤游标、无遗漏增量订阅或历史事件重放。                               |

Codeup 接入必须绑定实际服务版本及部署形态；不混用旧 `devops20210625` 与新版 `/oapi/v1` 契约，也不把中心版、Region 版路径和认证方式混在一起。

Codeup 阶段首先验证“新增源提交后，旧评审如何失效、能否证明评审对应版本”。若官方能力和真实验证仍不足，适配器返回证据不足，展示具体原因，不能通过请求头改名、只映射 `PASS` 或伪造提交关联来宣称支持。需要额外可信核验机制时另行评审，不自动放宽已确认的他人评审门槛。

## 4. 所有角色与代码托管平台共用的领域规则

- **版本：** PRD 和知识采用稳定文档身份加不可变修订，修订或恢复产生新候选；新草稿不替换当前发布版。
- **身份：** 服务端派生 Principal；Agent 凭据受项目、角色和操作范围约束并可撤销，不信任请求体自报 HUMAN。
- **权限：** 项目角色、知识库授权、发布资格和审批资格分别校验；正文、标题、索引、检索、快照与附件执行同一访问规则。
- **状态：** 通用任务和需求更新接口不得直接写入受保护阶段；DONE、TESTED、RELEASED 等由统一门禁产生。归档为独立授权动作。
- **工作状态：** 业务阶段、暂停／阻塞／返修／撤回等工作情况与当前版本有效性分别保存和展示；对应动作需有责任人、原因及继续条件，不能由状态改名跳过实际验收。
- **角色裁剪：** 定稿时显式声明参与角色及裁剪理由，不因缺少任务自动放行角色门槛。
- **历史与当前：** 历史发布、交付和批准保留；当前基线是否有效单独计算。更新相关输入后，直接关联任务和依赖链重评，不把所有无关任务一并重开。
- **并发：** 发布、认领、交付、批准及门禁重算使用 Serializable 事务，序列化冲突最多重试三次；每次重读当前状态，不沿用事务外旧对象。外部请求不在数据库事务中执行。
- **审计：** 批准、更正、撤销追加记录；禁止用覆盖或级联删除抹去已发布证据。合法删除和留存策略另行治理。
- **本地集成：** 角色工作流与正式协作状态分工明确；角色包、Agent 指令、流程路由和本地状态不得自行扩大授权或替代正式批准。
- **知识权威：** 发布正文及明确修订是权威，检索索引、摘要、切片和向量属于关联源版本的可重建派生物。产品负责业务需求与验收，技术事实和安全约束各有责任人；跨域冲突显式澄清，不能用“产品优先”覆盖已核实技术事实或安全底线。

## 5. 分阶段实施与出口

各阶段同步必要调用方和测试，不把仅建表、仅接口可调用或仅页面可显示算作闭环。核心阶段 S0–S6 完成 GitHub 首个闭环；Codeup 按 S7 的独立接入门槛验收。

### S0：统一契约、数据模型与实施基线

- 记录当前分支、未提交改动和验证结果，保留现有功能，不重置工作区。
- 统一共享类型、实际入参校验、响应、错误、分页及协议版本；复用锁定版本真正支持的 NestJS DTO 与 Swagger，不假定支持 OpenAPI 3.1。
- 先消除 PRD“每版新行”和“原行增版本”的双轨，统一修订、发布基线、上下文快照、任务版本、批准和事件关联。
- 将托管连接、仓库稳定引用、统一评审证据与能力声明纳入核心契约；GitHub 是首个实现，不是默认身份模型。
- 明确逻辑项目的多仓库关联、各仓库版本与跨仓交付证据，取消用单一项目目录或 repositoryUrl 隐含限定工程范围的做法。
- 定义角色工作流包、宿主适配、输入输出与共享检查点的最小契约，明确本地运行标识与平台需求／任务的关联；不建设中央角色步骤执行器。
- 定义默认包、项目定制与个人偏好的边界，以及流程配置发布版本、实例责任、澄清、阻塞、返修和恢复的共享契约；不将所有角色内部步骤提升成平台状态。
- 核心关系用外键；扩展追溯限定关系类型并校验端点和项目，唯一约束允许同端点的不同合法关系。

**出口：** 单一的事实、版本和门禁模型成立，厂商专属字段不向核心接口泄漏。

### S1：身份、项目权限与 Web 人工确认

- 增加可撤销 Agent 凭据，权限不超过授权者当前的项目权限；Agent 不具备发布、签字或授权管理能力。
- CLI 登录通过浏览器授权获取受限凭据，授权码绑定最初请求、限时核销；不得通过 URL 或日志交付凭据。
- Web 批准展示准确版本、工件摘要集合与厂商证据，密码二次验证产生五分钟一次性确认票据；最终事务重验并原子消费。
- 同一人可承担多个业务角色，分别记录决定；项目 OWNER/ADMIN 管理角色和知识库授权，不据此允许代码作者自审。
- Web 写操作检查 Origin／CSRF，密码只在请求内验证，凭据和确认票据不写业务日志。
- 本地工作流只取得完成其职责的受限能力；Skill 元数据、角色 persona、意图路由或本地人工继续按钮不产生平台发布和批准权限。

**出口：** 自报 HUMAN、跨项目使用凭据、撤销凭据重用、票据移用或重放均不能获得批准能力。

### S2：共享知识、角色工作流输入与上下文快照

- 复用现有正文库，将来源索引对齐到同一文档身份；不再保留独立的索引事实与正文事实。
- 候选、待审、发布、被取代和撤销语义明确；本地 approved 不构成可信发布，扫描缺席不删除发布历史。
- Git／Wiki 首版只显式导入候选，不做双向自动覆盖；稳定 ID 不随改名变化。
- 按知识库统一正文、索引、检索和快照权限，明确定稿发布者与候选写入者；必需内容无权获取或不存在时阻塞任务准备。
- 任务快照锁定定稿 PRD、相关已发布知识、工件、角色工作流与项目规范版本，并保存完整原始字节 SHA-256；快照固定内容，不固定以后访问权限。
- CLI 获取并校验正文后原子落盘，管理副本与草稿分开；不在 Agent 工作中途悄悄更换输入。
- 支持本地产品工作流将经授权的理解、决定落点和 PRD 作为候选登记，再经平台独立确认和发布；不能要求产品先有定稿 PRD 才能开始需求理解，也不把本地 approved 当作平台批准。
- 基础读取和检索不依赖外部模型；默认禁止外发，显式批准的项目与提供商限制覆盖应用管理的模型、摘要、向量和日志处理。
- 检索索引、摘要、切片和向量关联准确源修订，可丢弃后重建但不能反向改写发布事实；权限或撤销检查不能等待异步索引更新，检索和上下文不得继续泄露受限或已禁止使用的内容。必须适用的规则显式列入上下文，不靠语义检索偶然命中。
- 明确发布正文、修订、来源、权限、批准记录和必要附件的一致备份与恢复范围，并在隔离环境演练恢复。仅有迁移前备份或可重建索引，不等于共享知识已经可恢复。

**出口：** 作者电脑离线后，授权成员仍可取得相同发布版本，无权成员不能从标题、检索或快照泄露受限内容。

### S3：原子认领、显式释放与幂等交付

- ready 只读并返回版本及阻塞原因；claim 事务内校验当前角色、依赖有效性与预期版本，只允许一个执行者成功。
- 持久保存 claimId、认领主体和任务版本；责任人或管理员显式 release，递增版本并废止旧认领。
- deliver 关联当前认领和快照，使用完整字节摘要处理包括二进制在内的工件；本地自检、平台独立校验与人工判断分别记录。
- 保存幂等键、请求摘要及操作结果；先检查当前授权，再识别合法重放，同键同请求返回原结果，同键异内容拒绝。
- 幂等记录、工件与 REVIEW_PENDING 同事务；已关门任务不能追加新工件后继续沿用旧批准，不自动重放外部命令。
- 交付关联来源工作流版本和本地执行标识；本地阶段完成、文件存在或复选框勾选只能触发提交，不能直接置平台 DONE。
- 发布流程实例时落实任务责任、依赖和交接对象；阻塞或暂停期间限制不允许的正式写入，撤回不伪造完成。返工、恢复和重新认领共同检查当前基线及未决事项，不能沿用已废止的执行资格。

**出口：** 双认领单胜、释放后旧认领失效、响应丢失后重试不重复交付。

### S4：GitHub 首个适配器与统一代码门禁

- 按本计划第 3 节接口实现 GitHub；事件验签、delivery ID 去重、仓库身份校验和查询逻辑留在适配器。
- 按每位评审者的当前有效决定核验，记录 review ID、对应 SHA、评审者稳定 ID、合并事实与时间，处理重复、乱序、撤销及要求修改事件。
- 签字前读取核验当前源提交、任务关联、已合并事实和他人有效评审；排除代码作者和 Bot，不以 merge commit 代替评审提交。
- 核心只接收标准化证据；批准绑定快照、当前工件集合和预期版本，查询失败或证据不足时闭门。
- 批准及撤销追加保存；新定稿、PR 版本或有效评审变化使受影响任务重评，废止旧 claim，保留历史证据。
- 门禁输出结论、原因和针对的版本，Web 展示当前有效性而非“曾存在签字”。

**出口：** 用 GitHub 完成第一个厂商闭环，但核心及业务接口没有“只有 GitHub 才能成立”的条件。

### S5：可靠变更、本地工作流集成与 CLI／Web 交互

- 托管发布记录、当前指针、不可变变更事件及责任人快照同事务落盘；首版可靠拉取，不引入消息中间件。
- 确认按事件、责任人和角色独立保存并幂等；同人多角色分别确认，ack 不恢复旧批准。
- 无责任人的变更交项目 OWNER；管理员转派保留历史；先在数据库过滤授权和收件人，再用稳定游标分页。
- CLI 采用参数高于向上发现的工作区、高于全局默认的顺序；凭据按平台隔离，业务项目选择代码托管连接，而非凭一个可随意填写的 provider 字符串决定证据来源。
- 增加认证状态、doctor、中文起步说明；JSON 模式 stdout 只有单个结果，诊断走 stderr，错误和退出码可分类。
- Web 复用知识、PRD、看板与弹窗，提供发布、撤销、人工审批和厂商中立证据展示；CLI 打包包含必要规范资源。
- 将角色 SOP、模板和检查资源与工具入口分开维护，按声明支持的宿主生成 skill、命令或入口指针；记录包版本，验证重复安装、升级及无关文件保护。
- 为现有本地产品工作流提供契约适配，并用下游研发工作流验证产物交接、返修和恢复；不强制重写本地实现语言，不将工作流框架作为中心服务的必装依赖。
- 在宿主切换、离线和重试时从平台核对正式检查点，本地细节进度可保留；CLI 首版完整覆盖协作操作，未来 MCP 复用同一契约，首版不因引用 MCP 设计就宣称已提供服务。
- 提供项目流程定制的读取、校验、发布与选定版本能力，复用 Web 现有表单及 CLI 配置入口；支持按依赖并行、澄清、阻塞和返修交接，不新增可视化编排平台。

**出口：** 不同本地 AI 入口能够使用相同角色契约并接续已授权工作，CLI、Web 和直接 HTTP 执行同一权限及门禁；切换代码托管适配器不要求重写角色工作流。

### S6：迁移、验证和首版交付

- 新 API、Web、CLI、角色包和下发规范统一版本契约，移除旧旁路，不做旧 WorkMesh 契约兼容层。对已有本地工作流的主动集成不属于保留旧平台旁路，也不要求迁移其全部内部状态。
- 保留已有正文与原始证据；缺少版本或批准依据的数据不能自动转成有效发布或签字，数据映射和校验单独执行。
- 真实数据库迁移或重建另行确认目标、备份与影响；回滚不得重新开启已识别的授权旁路。
- 对齐部署说明、角色 SOP、工件规范、托管连接设置和能力说明；按角色包、宿主与代码托管平台记录验证范围，只显示真正已实现且验证过的能力。
- 观察认领冲突、幂等重放、门禁拒绝、过期快照、未确认变更和适配器核验失败，日志脱敏。
- 验证 Redis 缺席或故障不阻塞核心协作，并完成共享知识一致备份恢复演练；未取得这些证据时明确标记对应范围未验证，不用单元测试或进程存活替代。

**出口：** 核心与 GitHub 达到明确验收范围，Codeup 标为计划接入，而非已支持。

### S7：Codeup 公司项目接入

- 在公司授权后确认目标 Codeup 的版本、中心版／Region 版形态、服务地址、组织与仓库标识、只读权限和网络可达性；不从生产凭据或 GitLab 示例猜测契约。
- 独立实现 Codeup 请求认证、事件解析、合并请求及 PatchSet 查询、分页对账；业务门禁和角色工作流保持不变。
- 将 PASS／NOT_PASS 等转换为统一证据时保留原始语义及证明范围；没有评审与源提交关联依据时返回证据不足。
- 必测源分支追加提交、审批失效及重新评审、撤销或改为不通过、关闭／重开／合并、重复／乱序／漏通知、权限不足和限流。
- 对签字前取证与后续变更重评执行实际联调；不保证缺失的 Webhook 事件一定送达，使用 API 对账覆盖可发现的漏通知。
- 若当前公司版本不能提供满足门禁的证据，则不启用 Codeup 代码关门；报告限制并另行评审可信核验机制，不降级为只检查 merged 或 PASS。

**出口：** 获得明确版本、部署形态和证据范围的 Codeup 验收记录后，才对该范围标注支持。此阶段不自动获得访问公司项目或申请更高权限的授权。

## 6. 公共接口与 CLI 调整

| 子系统         | 接口及行为                                                                                                                       |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 身份           | 浏览器授权、受限 Agent 凭据创建与撤销、认证状态；Principal 由服务端确定。                                                        |
| 项目与仓库     | 一个逻辑项目绑定多个受授权仓库；任务、产物与代码证据明确各自仓库及版本，不依赖特定目录布局。                                     |
| 本地角色工作流 | 提供角色包及兼容信息、授权输入、正式检查点查询与候选／工件提交；不接收能任意执行本地脚本的流程定义。                             |
| 流程定制与实例 | 项目配置版本的校验、发布与选用；实例返回责任人、当前阶段、工作情况、基线有效性、阻塞原因及下一接手人，不以本地步骤结束替代批准。 |
| 任务           | GET ready；新增 POST claim／release；写入需要预期版本与有效认领。                                                                |
| 知识           | 候选提交、发布、撤销、指定修订正文获取；不接受本地声明直接获得发布资格。                                                         |
| 上下文         | 创建任务快照使用 POST；指定快照读取使用 GET，不因查询产生副作用。                                                                |
| 交付与批准     | 交付关联快照与幂等键；review request 与 Web 独立确认，通用状态更新不能关门。                                                     |
| 代码托管       | 项目配置已授权连接及稳定仓库引用；适配器承担事件校验、取证、能力查询及对账。核心批准关联内部评审证据 ID，而非 GitHub 专属 URL。  |
| 变更           | 事件和逐责任人确认分离；统一 items、nextCursor、hasMore 游标分页。                                                               |

CLI 公共协作路径：`login → doctor → ready → claim → context --task … --materialize → deliver → review → changes / ack`。这不是每个角色内部的完整 SOP；产品的检索、澄清、理解和出稿等步骤在本地角色工作流中组织，经授权后调用平台候选与评审接口。

`review` 只创建人工确认请求并提供 Web 链接，不能替人批准。CLI 业务命令不强制 GitHub 编号；请求引用、证据状态与连接厂商通过统一类型展示。移除能够绕开新模型直接签字的旧入口。

核心共用修订引用、快照、工件证据、代码评审证据、门禁条件、分页和错误契约，并有实际边界校验；TypeScript 类型不能代替验证。适配器对外不暴露通用“把任意外部数据认定为 APPROVED”的写接口。

## 8. 开源发布与公司部署边界

- 仓库已有 MIT 许可，但开源发布前仍须确认代码权属、依赖许可与必要声明；参考开源设计不等于自动完成发行合规。
- WorkMesh 源码开源不要求公司代码、知识、账号或部署实例公开；公司适配配置与凭据不进入示例或测试资料。
- 已观察到 Git 跟踪本机记忆与运行记录的文件名。公开前需经授权审查发行内容及历史，使用明确发行清单；仅改 ignore 或本机 exclude 不能消除已有历史。当前不读这些内容、不自动改写 Git 历史。
- 根 monorepo 保持 private 不妨碍源码开源。若发行 CLI 到 npm，只调整明确发行包的发布配置，校验包内容、依赖及规范资源，不把整个仓库打包发布。
- 角色包可包含通用 SOP、模板与辅助资源，但不包含示例公司的原始知识、客户资料、真实决定或凭据；直接复用外部框架代码、模板和脚本时核对许可与来源，不能把资料中的命令自动当作执行授权。
- 文档应按厂商、服务实例类型、API 版本和验证结果标注支持范围，不用“支持 Git”概括完整审批能力。

首版不实现 GitLab 审批、MCP 服务、自动租约接管、自动外部执行、多源双向编辑、实时协作编辑或供应链密码学签名。Codeup 不在这份暂缓清单中，而是本计划明确安排的 S7；它的真实公司接入仍受授权与证据能力条件约束。
