## 前三轮检查器缺陷与修正

前三轮使用同一输入 ZIP，输出目录分别为 `G:/workmesh-release-lifecycle-20261107-01`、`-02`、`-03`。它们的失败记录与日志保留，不能当作通过证据。这些问题发生在新检查器中。

| 轮次 | 实际缺陷与观察                                                                                                                                                                                                                                | 修正                                                                                                                |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `01` | 安装子进程已经退出，PostgreSQL 后代仍持有继承的输出句柄，检查器的 `ReadToEndAsync` 持续等待 EOF。对数据目录、可执行文件、命令行、PID 与监听端口核验所有权后，人工停止本轮 PostgreSQL 以解除等待；该轮最终以缺失 PostgreSQL PID 文件记录失败。 | 子进程改为隐藏启动并重定向至文件，按真实子进程退出码和超时判断命令结果，不等待后台后代的输出 EOF。                  |
| `02` | 文件重定向允许读取输出，但检查器尝试原地脱敏重写仍被后代持有的日志文件，收到文件占用错误。                                                                                                                                                    | 原始捕获放入隔离 `data/lifecycle-capture`，读取后另写独立的脱敏 `logs` 文件，不原地修改仍可能被后代持有的捕获文件。 |
| `03` | 已通过安装、20 个迁移、首次/冷/重复启动以及 `backup --verify`；查询确认临时验证数据库已移除时没有返回行，检查器对空 stdout 直接调用 `.Trim()` 发生空值错误。                                                                                  | 数据库查询结果先强制转换为字符串，再调用 `.Trim()`，允许合法的零行结果。                                            |

同时修正了 Windows 原生参数的引号和反斜杠转义。独立回归覆盖完整 JSON 读取、继承输出句柄不阻塞、日志脱敏、非零退出与超时真实失败、空格/引号/元字符/尾反斜杠保真和零行 SQL。最终 `04` 轮使用修正后的检查器完成整个链路。
