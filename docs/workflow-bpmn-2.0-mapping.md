# 内置软件交付流程的 BPMN 2.0 参考映射

本文把 `buildSoftwareDeliveryWorkflowTemplate()` 的依赖 DAG 映射到 BPMN 2.0 的泳道、网关和异常路径，供流程评审与后续建模使用。它是**概念映射与差距清单**：WorkMesh 当前保存和编译的是自定义 JSON DAG，不是 BPMN 2.0 XML，也没有宣称 BPMN 2.0 一致性或模型互操作能力。

## 泳道映射

以一个 WorkMesh 软件交付需求作为 BPMN Pool。角色通过步骤的 `roleKey` 形成逻辑泳道；这层泳道只是映射，定义中没有 BPMN `participant`、`laneSet` 或 `lane` 节点。

| BPMN 参与者／泳道          | WorkMesh 中的责任              | 主要映射任务                                                      |
| -------------------------- | ------------------------------ | ----------------------------------------------------------------- |
| 外部参与者：需求方         | 提供业务诉求及显式外部输入     | 消息起因／数据输入；不是当前 DAG 中的角色步骤                     |
| 产品（`product`）          | 形成 PRD，维护验收与发布责任槽 | `prd`；负责 PRD 发布槽及发布验收槽                                |
| UI（`ui`）                 | 有新视觉／交互时提供设计规格   | `design`，仅在模板启用 UI 时存在                                  |
| 后端（`backend`）          | 按 PRD 与已发布知识实现        | `backend`                                                         |
| 前端（`frontend`）         | 按 PRD、接口知识及可用设计实现 | `frontend`                                                        |
| QA（`qa`）                 | 派生用例并汇合验收             | `cases`、`accept`；承担任务验收槽                                 |
| 运维（`ops`）              | 组织发布                       | `release`                                                         |
| 项目审批人（人工泳道映射） | 对审批槽作出人工决定           | 各步骤的 `ALL` gate；由人员绑定与评审请求承载，不是单独的业务步骤 |

外部请求进入产品澄清、Git/CI 运行与证据、知识库取用，可视为消息／数据交换，但它们不是这张 DAG 中声明的 BPMN 任务或消息流。

## 关键流程与网关

模板的主要顺序流可读作：

```text
开始事件 → 产品: PRD
               ├─→ QA: 用例 ───────────────────┐
               ├─→ 后端: 实现 ──────────────────┤
               ├─→ 前端: 实现 ──────────────────┤→ QA: 汇合验收 → 运维: 发布
               └─→（可选）UI: 设计 → 前端实现 ─┘
```

这对应一组 BPMN **并行网关**的概念：PRD 完成后，QA 用例、后端实现和前端工作可并行推进；启用设计时，前端分支还要等待 UI 设计。`accept` 同时依赖 `backend`、`frontend`、`cases`，相当于并行汇聚点；`release` 等待验收步骤。

UI 开关是建流程时的模板选项，而非运行时判断：`excludeUi: true` 会移除 `design` 步骤，并让前端只依赖 PRD。这适合映射为建模时确定的不同流程版本；若将来需要按实例数据决定是否设计，应显式增加 BPMN **排他网关**及两条可追踪的分支。

审批槽采用 `ALL` 语义。可以映射为用户任务之后的人工批准等待／合并条件，要求所有配置的审批人满足条件才放行。编译器不支持 `ANY` 模式；审批不能画成可由 Agent 自行越过的自动网关。实现步骤的代码评审证据是服务端派生门槛。

## 异常、返修与终止路径

| 触发条件                                 | WorkMesh 已有行为                                                             | BPMN 2.0 参考表示与限制                                                                          |
| ---------------------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| 定义、角色包、输入来源或审批配置校验失败 | 编译无效，不能发布；缺少必需输入来源会产生编译问题                            | 流程定义阶段的错误／不可启动路径。当前没有单独的 BPMN Error Event 节点                           |
| 评审要求修改（`CHANGES_REQUESTED`）      | 绑定任务进入新 generation；旧 claim／工件失效，依赖它的下游结果按依赖关系失效 | 可映射为返修回路及下游重做；当前通过任务与 generation 语义表达，不是显式 BPMN sequence flow loop |
| 审批拒绝（`REJECT`）                     | 绑定任务回到 `OPEN/BLOCKED` 并保留拒绝原因，候选不发布                        | 可映射为带终止或待处理结果的拒绝分支；系统未把它等同于普通返修                                   |
| QA 验证步骤被省略                        | 有角色包契约时，需声明验证豁免理由和审计引用                                  | 可映射为显式例外分支／补偿依据；当前是编译期豁免元数据，不是运行时网关                           |
| 外部输入缺失、执行超时或基础设施故障     | 现有 DAG 没有定义通用 SLA、定时器、重试次数、人工升级或死信语义               | BPMN 可用中断边界事件、定时器、错误事件及异常处理子流程表达；这些需要在流程协议中另行定义        |

## 与 BPMN 2.0 的差距及后续准入

现有 `deps` 表达有向无环依赖，`roleKey` 表达任务归属，`gates` 表达必须满足的审批条件，`inputBindings` 表达显式输入来源；这些字段足以支持上述评审映射，但不能覆盖完整 BPMN 语义。目前没有 BPMN XML 导入／导出、图形布局、事件定义、消息流、边界事件、子流程、补偿、循环活动或标准模型校验。因此，图示只能帮助人审视先后、并行和异常处理，不应标注为 BPMN 2.0 可执行模型。

若要声明 BPMN 2.0 兼容，至少还需：选定并记录 BPMN 2.0 规范子集；为角色任务、人工审批、并行分支、返修、拒绝、输入等待及运维失败定义可交换的 BPMN 元素；提供 XML 往返测试和标准校验器结果；验证导入后保留审批、工件、证据与审计语义。完成这些之前，本文件只作为对内映射与差距评审。
