# ReqFlow 协作规范 v0.1（草案）

> 本文定义 ReqFlow 项目的协作契约。**规范优先于实现**：任一角色（人或其本地 AI）在参与项目时，必须先遵守本规范，否则其产出无法被平台装配、校验和追溯。
> 状态：草案，待评审。示例项目：易番番。

---

## 1. 定位

ReqFlow 不是一个"需求管理系统"，而是**项目事实的联邦层**：

- 每个角色在自己电脑上、用自己的 AI（Claude Code / Codex / WorkBuddy / 其他）干活；
- 平台不占有任何人的知识内容，只维护**事实、指针与挂靠关系**；
- **产品是源头**：产品的项目知识库是上游权威事实，其他角色的知识库是本地派生事实；
- 平台向下为每个角色的 agent **装配上下文**，向上**回收证据**并**传播变更**；
- Web 页面只承担进度视图职责，不是工作界面。

一句话：**大家不在一起工作，但在同一个事实上工作。**

## 2. 术语

| 术语                     | 含义                                                                |
| ------------------------ | ------------------------------------------------------------------- |
| 需求（Requirement）      | 产品定义的最小协作单元，全局唯一编号 `REQ-<数字>`                   |
| 工件（Artifact）         | 任一角色交付的、可校验的产出（PRD、设计、实现说明、用例、发布记录） |
| 证据（Evidence）         | 工件中可机器校验的部分（commit hash、用例执行结果、发布版本号）     |
| 挂靠（Anchor）           | 声明某段本地知识或某个工件归属于哪条需求                            |
| 上下文包（Context Pack） | 平台按需求装配、供 agent 开工使用的结构化上下文                     |
| 状态门（Gate）           | 需求状态流转的准入条件：工件存在 + schema 校验通过 + 人已签字       |

## 3. 核心原则

1. **产品源优先**：任何冲突以产品定稿的需求与验收标准为准，agent 不得自行解释或改写。
2. **内容留在本地**：各角色知识库内容不迁入平台，平台只同步索引与挂靠关系。
3. **一切锚定需求编号**：没有 `REQ-xxx` 的产出不进入追溯链。
4. **规范可执行**：规范以文件形态下发到本地工作区，工件提交时经机器校验，不合格不放行。
5. **AI 生产，人签字**：AI 完成生产环节，人只在状态门签字；签字即责任记录。

## 4. 锚点规范

### 4.1 编号格式

需求编号必须携带**项目唯一标识**：

```
<PROJECT_KEY>-REQ-<序号>      例：YFF-REQ-123（易番番）、CRM-REQ-45
```

- `PROJECT_KEY` 在项目创建时确定，2–6 位大写字母，**一经使用不可变更**（改名需走编号迁移）；
- 序号在项目内自增，跨项目独立；
- 平台内所有展示、接口、URL 均使用完整编号，禁止省略前缀。

### 4.2 编号必须出现的位置

| 载体           | 约定                                                                                   |
| -------------- | -------------------------------------------------------------------------------------- |
| Git 分支       | `feat/YFF-REQ-123-<简述>`、`fix/YFF-REQ-123-<简述>`                                    |
| Commit message | 正文或 footer 含 `YFF-REQ-123`；建议 `feat(scope): 描述 (YFF-REQ-123)`                 |
| Pull Request   | 标题前缀 `[YFF-REQ-123]`，描述含 `Closes YFF-REQ-123`                                  |
| 测试用例       | 用例 ID `TC-YFF-REQ-123-<序号>`，用例文件内声明 `req: YFF-REQ-123`                     |
| 设计稿         | 文件命名 `YFF-REQ-123-<页面>.fig / .png`，front-matter 或描述区声明 `req: YFF-REQ-123` |
| 本地知识条目   | 文件 front-matter 必须含 `req: YFF-REQ-123`                                            |
| 发布记录       | 记录体必填 `requirements: [YFF-REQ-123]`                                               |
| 任务           | 任务 ID `YFF-REQ-123-T01`，见 §5.6                                                     |

**缺失锚点的产出视为无效工件**，平台拒收并记录。

## 5. 角色工作流

每个角色的完整 SOP（分阶段动作、DoD 自检清单、交接与协同规则）见
**《角色工作流规范 v0.1》**（`docs/role-workflows-v0.1.md`），包含产品 / UI / 前端 / 后端 / 测试 / 运维
六套工作流，以及角色间协同协议（交接、回问、变更传播、多人并行、裁剪规则）。

无论使用何种 agent 工具，各角色都必须遵守同一套工作流与协同协议。

每个角色的流程骨架固定为：**拉上下文 → 生产 → 自检 → 回交 → 等签字**。

### 5.1 产品（源头）

- 输入：业务诉求、用户反馈、上一版需求
- 步骤：建需求 → 撰写/更新 PRD → 自检（验收标准是否可测）→ 提交评审
- 产出：`prd.md`（含验收标准章节），挂 `REQ-xxx`
- 出口：评审签字 → 状态推到 `PRD_READY`
- 特别约束：PRD 定稿后即为权威事实，任何变更必须走版本更新并触发变更传播

### 5.2 UI

- 输入：定稿 PRD + 现有设计规范
- 步骤：拉上下文 → 出设计稿与交互说明 → 标注验收相关的界面约束 → 回交
- 产出：设计文件 + `design.md`（页面、状态、边界条件），挂 `REQ-xxx`
- 出口：产品与设计负责人确认 → `DESIGN_READY`

### 5.3 前端 / 后端

- 输入：`reqflow context YFF-REQ-123` 装配的上下文包（PRD + 设计约束 + 技术知识库相关条目 + 历史 commit）
- 步骤：读上下文 → 出实现方案 → 编码 → 自测 → 提交（commit/PR 带编号）→ 回交实现说明
- 产出：代码（commit/PR，自动回链）+ `impl.md`（改动范围、受影响接口、遗留项）
- 出口：代码评审签字 → `CODE_LINKED`
- 特别约束：实现与 PRD 冲突时必须回问（`NEEDS_CLARIFY`），不得自行变更验收标准

### 5.4 测试

- 输入：同一份上下文包 + 已回链的代码范围
- 步骤：拉上下文 → 生成用例 → 执行 → 结果回写 → 缺陷挂需求
- 产出：`cases.yaml`（用例 + 执行结果），缺陷条目挂 `REQ-xxx`
- 出口：用例评审 + 结果确认 → `TESTED`

### 5.5 运维

- 输入：已测试通过的需求范围 + 部署手册
- 步骤：拉上下文 → 发布 → 冒烟 → 记录发布证据
- 产出：`release.md`（版本号、时间、环境、影响需求列表）
- 出口：发布确认 → `RELEASED`

### 5.6 任务层（Task）

需求与代码之间必须有任务中间层，否则多人并行同一需求时追溯粒度会糊掉。

- **任务来源**：由 PRD / 技术方案拆解产生，一条需求可拆多个任务，每个任务归属一个角色；
- **任务编号**：`<需求编号>-T<两位序号>`，例 `YFF-REQ-123-T01`；
- **任务必填字段**：标题、所属需求、负责角色、负责人（人或 agent）、验收点、依赖任务；
- **依赖关系**：`blocks / blocked-by / related / discovered-from`，平台据此计算可执行队列；
- **状态**：`OPEN → IN_PROGRESS → REVIEW_PENDING → DONE`，**agent 只能推进到 `REVIEW_PENDING`，不得自行置为 DONE**；
- **回链**：commit / PR 优先挂任务编号（`YFF-REQ-123-T01`），平台自动向上聚合到需求；
- **查询**：`reqflow ready --json` 返回的是本角色"未被阻塞的任务"，而非需求。

## 6. 上下文获取规范

**agent 开工第一动作固定为拉取上下文包**，禁止依据聊天记录、记忆或代码推测需求。

```
reqflow context YFF-REQ-123            # 人可读
reqflow context YFF-REQ-123 --json     # agent 使用
```

上下文包内容（按优先级）：

1. **产品源**（权威）：需求描述、定稿 PRD、验收标准、版本历史
2. **跨角色工件**：设计约束、已有实现范围、已有用例
3. **角色本地知识**（指针）：本角色知识库中挂靠该需求的条目位置，内容由本地 agent 自行读取
4. **历史证据**：关联的 commit、PR、发布记录

冲突处理优先级：产品源 > 跨角色工件 > 本地知识 > agent 自身推断。

## 7. 知识库形态与挂靠规范

### 7.1 形态决策：本地 Markdown 文件 + YAML front-matter + Git 版本化

**首选形态**（各角色本地知识库统一采用）：

```
.reqflow/knowledge/<role>/
  index.md        # 人/agent 可读的导航目录（llms.txt 风格：一句话摘要 + 链接）
  log.md          # 变更日志
  index.jsonl     # 机器索引，sync 上报用（每行一条：id/标题/路径哈希/挂靠需求/更新时间）
  <topic>/*.md    # 一条知识一个文件
```

选择依据（对齐开源生态已收敛的做法）：

- **Markdown + front-matter 是 agent 时代的事实标准**：AGENTS.md（Linux 基金会托管，6 万+ 项目、30+ 工具支持）、CLAUDE.md、SKILL.md、llms.txt 全部收敛到这一形态；Google 的 Open Knowledge Format 也定义为"Markdown 文件目录 + YAML front-matter"。agent 天生会读文件，无需任何适配；
- **Git 天然提供版本、审计与多机同步**：与 beads 的 `.beads/issues.jsonl` 同一思路，不需要额外服务器；
- **工具可任选**：Obsidian / Logseq / VS Code 都能直接编辑同一批 Markdown 文件，平台不与任何笔记工具绑定；
- **Notion / 飞书 / Confluence 等云端库**：列为**外部知识库**（次选）。它们只能通过导出或 MCP 只读适配，且必须能导出为 Markdown 才能挂靠——**平台不认可无法导出、无法版本化的知识源**。

### 7.2 条目 front-matter

```markdown
---
id: k-8f3a2c # 稳定 ID（路径哈希），改名不丢挂靠关系
req: YFF-REQ-123 # 挂靠需求，必填
role: frontend # 归属角色
status: approved # approved | draft（draft 不进入上下文装配）
updated: 2026-10-31
---
```

- **知识库 vs agent 记忆**：只有 `status: approved` 的条目属于"已确认事实"，可挂靠、可进上下文；agent 自己观察到的内容属"观察记录"，不得直接写入知识库，必须经人确认后转 `approved`。这条边界必须守住，否则错误会被后续会话当成事实继承。
- 一条知识只讲一件事；跨多需求的内容拆成多条分别挂靠。

### 7.3 上报与传播

- 本地 agent 执行 `reqflow sync` 时，**只上报索引**（条目标题、路径哈希、挂靠需求、更新时间），不上报正文；
- 平台据此建立「知识条目 ↔ 需求」挂靠边，用于上下文装配与变更传播；
- **变更传播**：产品更新 `YFF-REQ-123` 并定稿后，平台向所有挂靠该需求的知识、代码、用例所属角色推送变更通知，要求确认或更新。

## 8. AI 行为准则（红线）

所有角色的 agent 必须遵守：

1. 不臆造需求：未在产品源中出现的功能，不得实现；
2. 不改验收标准：发现 PRD 有问题，标 `NEEDS_CLARIFY` 回问，不自行修改；
3. 不跳过锚点：任何产出必须携带需求编号；
4. 不确定即声明：无法判断时输出 `NEEDS_CLARIFY` 并说明依据缺口，而非自行假设；
5. 只交证据不交结论：提交的是可校验的工件与证据，而非"我认为已完成"的陈述；
6. 遵守角色边界：不越权修改其他角色的工件（前端不改用例，测试不改 PRD）。

## 9. 状态机与门槛

```
DRAFT → PRD_READY → DESIGN_READY → IN_DEV → CODE_LINKED → TESTED → RELEASED
```

| 状态           | 进入条件                                                      |
| -------------- | ------------------------------------------------------------- |
| `PRD_READY`    | 存在 `prd.md` 且通过 schema 校验 + 产品签字                   |
| `DESIGN_READY` | 存在 `design.md`/设计附件 + 产品与设计确认                    |
| `IN_DEV`       | 至少一个任务进入 `IN_PROGRESS`                                |
| `CODE_LINKED`  | 关联任务全部 `DONE` + commit/PR 已回链 + `impl.md` + 评审签字 |
| `TESTED`       | 存在 `cases.yaml` 且用例覆盖验收标准 + 结果已记录             |
| `RELEASED`     | 存在 `release.md` + 发布确认                                  |

任务层状态独立流转：`OPEN → IN_PROGRESS → REVIEW_PENDING → DONE`，
需求状态由平台依据关联任务的聚合结果自动推进，人只在需求级状态门签字。

### 9.1 签字规则（混合模式）

**原则：AI 生产，人关门。任何环节都不得由 agent 自行宣告完成。**

| 环节              | 签字方式               | 机制                                                              |
| ----------------- | ---------------------- | ----------------------------------------------------------------- |
| 代码（前端/后端） | **PR review 隐式代表** | GitHub/GitLab 上 approve 后，webhook 同步为签字证据，无需额外动作 |
| PRD 定稿          | 平台内签字             | 产品在平台确认，记录签字人与时间                                  |
| 设计确认          | 平台内签字             | 产品 + 设计负责人确认                                             |
| 用例确认          | 平台内签字             | 测试负责人确认                                                    |
| 发布确认          | 平台内签字             | 运维确认                                                          |

规则细则：

1. agent 只能把任务推进到 `REVIEW_PENDING`，**禁止提交 `DONE`**；平台对 agent 身份的 `DONE` 请求一律拒绝；
2. PR review 证据需包含：reviewer 身份、approve 时间、对应任务编号，缺失任一项不视为有效签字；
3. 每个签字动作记录：对象（需求/任务）、环节、签字人、时间、依据（PR 链接或平台确认）；
4. 签字不可撤销，只能通过**追加一条新的反向记录**更正（保留审计链）；
5. 需求级状态门 = 关联任务全部 `DONE` + 各环节签字齐全 + 工件校验通过，三者缺一不放行。

**门槛为硬约束**：schema 校验失败或缺少签字，状态不得流转。

## 10. 接口约定（桥接器）

每个角色的本地工作区通过统一桥接器与平台交互，命令面固定：

| 命令                             | 用途                                          |
| -------------------------------- | --------------------------------------------- |
| `reqflow init --role <role>`     | 初始化本地工作区，下发规范文件                |
| `reqflow ready --json`           | 查询本角色可执行的工作（未被阻塞的需求/任务） |
| `reqflow context REQ-xxx --json` | 拉取上下文包                                  |
| `reqflow deliver`                | 提交工件与证据（含锚点与 schema 自检）        |
| `reqflow sync`                   | 上报本地知识索引与挂靠关系                    |

同一套能力同时以 MCP 工具暴露，供不支持 CLI 的 agent 直接调用。

## 11. 规范下发形态

规范不是 wiki 文档，而是随项目下发的文件：

```
.reqflow/
  SPEC.md                # 全局契约：锚点、红线、上下文来源
  roles/
    product.md           # 各角色工作流 SOP
    frontend.md
    backend.md
    qa.md
    ui.md
    ops.md
  artifacts/
    prd.schema.md        # 工件格式与校验规则
    cases.schema.yaml
```

`reqflow init --role <role>` 写入工作区，并写入 agent 入口文件（AGENTS.md / slash command），
使该角色的 AI 每次开工自动加载本规范。

## 12. 落地路径（v0.1 验证）

1. 选取一条真实需求（建议：本地模型接入）作为 dogfooding 对象；
2. 以本人同时承担产品与开发两角色，跑通：建需求 → 定稿 PRD → 拉上下文 → 编码 → commit 回链 → 追溯可见；
3. 补齐桥接器命令与工件校验；
4. 引入第二个角色（测试）验证规范可复制性；
5. 逐步扩展到 UI、运维。
