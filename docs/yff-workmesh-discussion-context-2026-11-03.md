## 3. WorkMesh 当前已有能力

根据本次本地源码检查，已有以下能力：

- 创建项目和业务角色。
- 创建项目时自动生成默认产品知识库。
- 浏览器设备授权和 CLI 角色包安装。
- 任务认领。
- 创建上下文快照，并校验后物化到本地。
- 提交 `UNDERSTANDING`、`PRD`、`KNOWLEDGE`、`DECISION` 等文档候选。
- 人工评审、发布文档。
- 提交任务工件，进行验收和发布审批。
- 保留文档修订和发布历史。

`setup` 负责授权、角色包安装和项目绑定等初始化，不负责自动理解历史代码、生成完整项目知识库。

## 5. 建议新增“历史项目接入/初始化”功能

这是讨论提出的新功能方向，尚未实施。

建议分为三个阶段：

| 阶段       | 作用                                        |
| ---------- | ------------------------------------------- |
| 扫描       | 盘点代码、配置和已有文档，记录来源          |
| 生成草稿   | 由静态分析和 Codex 整理项目知识，标记未知项 |
| 提交与发布 | 提交为知识候选，由负责人审核发布            |

以下是建议的新命令，不是当前已有命令：

```powershell
workmesh onboard scan
workmesh onboard submit
workmesh onboard rescan
```

首次扫描建议覆盖：

- 仓库结构、当前 commit、子项目和服务。
- 语言、框架、依赖和包管理器。
- 启动、构建、测试命令。
- 数据库 schema 和迁移。
- API 路由、模块边界、外部依赖。
- Docker、CI/CD、部署配置。
- README、历史需求、架构决策和运行手册。

生成的知识应包含来源文件、来源 commit 和待确认事项。业务规则、历史原因等无法可靠从代码推导的内容，需要负责人补充确认。

建议先在本地生成草稿，再明确选择哪些内容提交。知识库记录环境变量名称、用途和配置方式，不保存实际密码、Token、私钥等值。

增量更新应生成新候选修订，保留人工整理内容。扫描时没有发现某个文件，不能直接视为应删除已有知识。

## 6. 易番番建议准备的知识库

建议按照三类知识组织：

| 类型                | 回答的问题                   | 主要内容                                                   |
| ------------------- | ---------------------------- | ---------------------------------------------------------- |
| `BUSINESS` 业务知识 | 产品为什么这样做，规则是什么 | 产品概览、术语、角色权限、业务流程、状态规则、历史兼容约束 |
| `SYSTEM` 系统知识   | 系统如何组织、如何运行和修改 | 架构、模块地图、启动、接口、数据库、测试、部署回滚         |
| `PRACTICE` 团队实践 | 团队和各角色怎样工作         | 开发规范、评审规则、测试检查表、发布流程、Codex 使用约定   |

易番番程序启动本身不依赖 WorkMesh 知识库。知识库用于帮助成员和 Codex 理解项目并开展协作。

历史项目接入时，建议优先整理：

```text
项目概览
本地启动说明
模块地图
环境变量和外部依赖
测试和构建方式
业务术语与关键规则
部署与回滚说明
```

这些是首批内容建议，不是已经核实的 WorkMesh 强制准入条件。

不需要穷尽整个历史项目的所有知识后才开始开发。可以先整理公共基础知识和第一个需求涉及的模块，然后在实际使用中补充。

## 7. 产品知识库的当前状态

WorkMesh 创建项目时，会自动创建：

```text
名称：产品知识库
key：product-knowledge
kind：BUSINESS
visibility：PROJECT
```

框架已经有产品知识库能力。但本地存在 `G:\yesgoo\yff` 目录，不代表已经与 WorkMesh 中某个项目建立绑定，也不代表平台中已有真实、完整的易番番资料。

本次没有检查运行中的易番番项目数据，仍需确认：

- WorkMesh 中哪个项目代表易番番。
- 该项目的 UUID。
- 产品知识库 UUID。
- 已有文档、候选和正式发布内容。
- 当前账号是否能读取、提交和发布这些资料。

实现上还有一个限制：数据库模型已有知识库 `kind` 字段，但当前普通创建知识库 API 未开放 `kind` 入参。默认产品库由项目创建逻辑明确设为 `BUSINESS`，普通新增知识库则使用数据库默认的 `SYSTEM`。

因此，三类知识库的分类设计已有基础，但不能理解为当前 Web/API 已完整支持三类库的全部创建和管理流程。相关架构文档中的部分闭环仍是设计，不是已实施能力。

## 8. PRD 发布时实际更新什么

当前 PRD 和长期知识文档共用文档存储、修订与发布机制，但文档类型和业务用途不同。

PRD 候选提交时已经归属于一个知识库。所有必需审批槽通过后，系统会：

1. 将该 PRD 文档的当前发布指针指向批准的修订。
2. 增加文档版本并追加发布记录。
3. 更新需求的当前 PRD 指针和交付范围。
4. 推进需求版本、代次和阶段。
5. 将同一文档上其他未决评审置为失效。

这些操作在同一数据库事务中完成。历史修订保留，不通过覆盖正文来删除旧版本。

```text
PRD 候选
→ PRD_PUBLICATION 评审
→ 必需审批槽全部通过
→ 文档当前发布版本更新
→ 需求当前 PRD 基线更新
→ 后续任务获取相应的已发布 PRD
```

后续任务获取上下文时，会根据需求基线读取相应的已发布 PRD。旧上下文不会在本地被静默替换；基线或版本发生变化后，需要按当前任务状态重新获取有效上下文。

## 9. PRD 发布与长期知识更新的区别

目前不会自动把 PRD 的内容抽取、合并到其他业务规则、架构说明、接口契约等长期知识文档中。

```text
PRD 正式发布
= 确认本需求的正式目标、范围和验收基线
```

```text
长期知识更新
= 将可复用的业务规则、技术事实和工程经验，
  作为独立知识文档的新建候选或新修订进行发布
```

当前可行流程：

```text
PRD 发布
→ 开发、测试、验收
→ 提炼可复用知识
→ 提交 KNOWLEDGE / DECISION 候选
→ 独立知识评审
→ 发布长期知识
```

长期业务事实和系统事实最好结合实际实现与验收结果确认。PRD 发布说明方案获批，不等于功能已经实现上线。

新建知识文档时使用 `--kb` 指定知识库；修改既有知识时应针对原文档提交新修订，避免不断创建重复文档。当前 CLI 支持 `--document` 指定已有文档。

讨论提出未来增加“从 PRD 和交付结果提炼知识”的能力：

- 识别新增或改变的业务规则。
- 找出需要更新的已有知识文档。
- 生成差异草稿和来源引用。
- 提交为独立知识候选。
- 由相应负责人审核后发布。

这个自动捕获、提炼和更新闭环目前尚未完成。

## 10. 日常开发流程与接入流程的关系

历史项目接入完成后，日常开发可按以下方向组织：

```text
首次接入：
仓库与文档盘点
→ 知识草稿
→ 人工确认并发布
→ 工作区授权与角色绑定

日常需求：
创建需求并明确验收标准
→ 准备流程和责任人
→ 认领任务
→ 获取并物化上下文
→ Codex 读取代码和相关知识后实现
→ 测试与交付
→ QA / Owner 审批
→ 发布后沉淀长期知识
```

平台项目 UUID、知识库 UUID、任务 ID、claim ID、snapshot ID 和任务版本均应使用当前实例实际返回的值。项目 key 不应直接替代要求 UUID 的参数。
