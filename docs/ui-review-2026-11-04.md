# WorkMesh Web UI 页面级体验审计与优化建议

> 日期：2026-11-04 · 范围：`apps/web`（React 18 + Vite）全部 15 个路由页面 + 全站壳层
> 方法：以 owner 账号（`owner@yesgoo.local`，演示数据 25 需求 / 48 任务 / 73 评审 / 52 文档）真实登录，在 1440×900、1024×768、390×844、320×844 四个视口逐页走查关键任务流；结合源码、DOM 实测尺寸、对比度计算与接口响应取证。
> 证据口径：文中的 **【事实】** 均有 file:line、截图或实测数值支撑；**【推测】** 是对使用频率/团队规模的推断，不当作结论。截图索引见文末附录。
> 与既有文档的分工：`docs/usage-optimization-2026-11-04.md` 回答「用它干活哪里断」，覆盖 CLI/运维/流程；**本文只回答「浏览器里的页面为什么难用、先改哪一处」**，不重复其结论，只在重叠处标注「同源」。

## 0. 结论：骨架是对的，页面层把顺序和位置做错了

**WorkMesh 的 Web 端不是"设计不好看"，而是"该在第一屏的东西不在第一屏、该拦住用户的错误留到最后一秒、该说人话的地方说了机器话"。**

产品骨架值得保留：证据—摘要—票据的审批模型、`PageState/EmptyState/ErrorState/StaleDataBanner` 四态语义、`Modal` 的焦点陷阱与图层栈、项目上下文的 Zustand 状态机、DiffViewer 的行号/折叠、看板"状态待确认"的诚实表达——这些在同类内部工具里都算做得好的。问题集中在页面层：

**五个最痛的点（P0）：**

1. **会话引导失败会把用户永久锁在白屏**。一次 429/断网后 `bootstrapSession` 失败只弹一条 3.6 秒消失的 toast，`authStore.status` 永远停在 `loading`，页面只剩一行「正在建立会话…」，没有重试、没有倒计时、导航和侧栏都不渲染。连续访问 8–12 个页面或多人共享出口 IP 时会自然触发限流（本次审计主控与子审计合计真实触发 3 次）。【事实】`App.tsx:74-79,225-232`；截图 `.tmp/ui-review/shots/roles.png`、`d2-reviews.png`
2. **评审决定页把"作出决定"放在 1788px 处，且页面先说"证据完整"再说"缺少有效证据"**。桌面抽屉正文 2019px/可视 820px，移动端 2338px/744px；批准按钮 `disabled=false`，用户走完 5 次点击 + 一次密码（密码二验限 5 次/15 分钟）后才被服务端以 `CODE_REVIEW_EVIDENCE_MISSING` 拒绝。签字是这个产品的核心动作，这里同时存在"藏主操作"和"自相矛盾"。【事实】`ReviewDecision.tsx:586-599,1052-1090,1324-1336`；截图 `d3-review-decision.png`
3. **需求详情首屏被 1407px（移动 1856px）的装饰性机器人流程图占满**，页签在 1615px；流程图里 13 张头像来自第三方 `text_to_image` 外链（URL 含角色信息），断网即破图，与"数据不出域"的定位冲突。【事实】`RequirementDetail.tsx:1324-1334`、`RequirementPipeline.tsx:72-75`；截图 `d2-requirement-detail.png`、`m3-requirement-detail.png`
4. **移动端核心路径不可用**：需求列表 751px 表格塞进 356px 滚动区，标题竖排一字一行、操作列在屏外；评审列表的"打开评审"同样在横向滚动区外；工作台首屏 0 条待办（统计卡高 590px，tab 在 1237px）；需求详情整页 6060px。【事实】截图 `m3-requirements.png`、`m3-reviews.png`、`m3-home.png`、`m3-requirement-detail.png`
5. **加载/失败被静默伪装成"没有数据"**：项目、知识库、PRD 三页请求失败时，错误码和"还没有可访问的项目 / 该项目还没有文档"同屏显示；知识库 52 个文档只显示 50 个还写"共 50 条"；活动流 429 被 catch 成空数组显示"暂无审计事件"。【事实】`Projects.tsx:113-117,171-175`、`Knowledge.tsx:138-154`、`App.tsx:115-129`；截图 `projects-error.png`、`knowledge-error.png`

**一句话排序：先把"失败可恢复、主操作可见、假数据不出现"这三类修掉，再谈视觉统一。**

## 2. 全局问题：每一页都在承受的系统性缺陷

### 2.1 【P0】会话/限流/失败恢复：一次失败 = 白屏 + 无从下手

**现象【事实】**

- `App.tsx:74-79` 的 `bootstrapSession().catch()` 只 `toast.error(formatApiError(caught))`，不改 `authStore.status`；`store/auth.ts` 中 status 只在成功时变 `authenticated`。于是 `App.tsx:225-232` 永远渲染 `<section className="page-card muted">正在建立会话…</section>`。
- toast 3.6 秒后自动消失（`store/toast.ts:21-27`），屏幕最后只剩一行灰字，导航/侧栏/内容全空，**连"刷新"以外的任何操作入口都没有**。
- 429 的实际文案是 `[HTTP_429] 请求失败（HTTP 429）`：服务端返回 `{message:'请求过于频繁'}` + `Retry-After` 头（`main.ts:42-45`），但 `client.ts:88-99,146-167` 只认 `payload.error` 信封、不读 `Retry-After`、不读 `details.retryAfterSeconds`，也没有退避。
- 同一时刻重复弹两条完全相同的 toast（无去重）；401 会话过期也是 `[UNAUTHENTICATED] 会话已过期` 原始码 ×2。
- 点"刷新"不会冷却：实测连点两次"刷新"把一次失败变成 6 次请求，继续烧配额。
- 同类问题：`/api/health` 只在挂载时查一次（`App.tsx:136-140`），一旦失败，左下角永远显示"API 未连接 / LINK OFFLINE"，网络恢复 6 秒后仍然离线且不再请求（实测 `healthHits` 停在 2）；页面上同时出现"API 已连接"和"工作台加载失败"的矛盾信息。
- 通知中心的活动列表请求失败被 `.catch(() => setRecentActivity([]))` 吞掉（`App.tsx:115-129`），显示"暂无审计事件。"——用户以为没有活动，实际是请求失败。

**用户影响**：网络抖动、限流窗口、服务重启——任何一种都会让非技术用户以为"系统坏了/被踢了"，唯一的出路是自己猜"刷新试试"；即使刷新，若仍在限流窗口内会继续失败。对一个"签字即事实"的审批工具，**最不该在失败时丢掉导航与重试入口**。

**改法（按顺序）**

1. `authStore` 增加 `error` 状态：`bootstrapSession` 失败 → 渲染 `ErrorState`（标题"暂时无法连接服务器"，副文案区分 401/429/网络，带"重试"与"返回登录"），不要把失败塞进 `loading`。（S）
2. `ApiError` 增加 `retryAfterSeconds`（读响应头与 `details`），`formatApiError` 对 429 输出"请求过于频繁，请约 N 秒后重试"，页面/Toast 共用；toast 按 `code+message` 去重（保留最新一条）。（S）
3. 429 全局冷却：一个进程内的 `rateLimitedUntil`，冷却期内请求直接返回可读错误而不是继续打服务端；刷新按钮在冷却期显示倒计时并禁用。（M）
4. 健康检查周期化（如 30s + `online/offline` 事件 + 点击重试），且失败时不要与业务数据错误叠加展示；通知中心改成 加载/空/失败 三态。（S）
5. 失败态一律用现有 `ErrorState`（已支持折叠技术详情 + requestId），禁止 `<p className="error">{formatApiError()}</p>` 裸奔。（S）

**截图**：`.tmp/ui-review/shots/roles.png`（会话 + 429 白屏）、`d2-reviews.png`；`.tmp/ui-review/team-shots/crosscut/429-session-stuck.png`、`crosscut 401-session-expired*.png`

### 2.2 【P1】状态反馈不统一：新组件建好了，只有一页在用

**现象【事实】** 团队在 2026-11-03 提交了 `PageState/EmptyState/ErrorState/StaleDataBanner`（`docs/design/ui-foundations.md` §3），但实际采纳率极低：`grep` 统计 `PageState` 仅 Pipeline.tsx 使用（4 处），其余 12 个页面 0 处；`Projects/Knowledge/Prds/Workflows/Roles/Authorization/Profile` 连 `loading` 状态都没有（0 处），首屏必然先闪"空数据"，慢网/失败时尤其明显。典型表现：

| 页面         | 加载中                                                 | 请求失败                                | 真实空       |
| ------------ | ------------------------------------------------------ | --------------------------------------- | ------------ |
| 需求列表     | 无骨架，显示"需求列表 0/0""还没有需求，先在上方创建。" | 顶部红字 `[CODE]…`，列表保持空          | 同一句文案   |
| 项目         | 无，表格短暂空白                                       | 红字 + "还没有可访问的项目"同屏，无重试 | 同一句文案   |
| 知识库       | 无，"文档 0/0"                                         | 红字 + "该项目还没有文档"同屏，无重试   | 同一句文案   |
| PRD          | 无                                                     | 红字直出，页面顶部残留                  | 同上         |
| 通知中心活动 | 无                                                     | 请求失败被吞 → "暂无审计事件。"         | 同一句文案   |
| 工作台       | 有 `PageState`/骨架（好）                              | `ErrorState` + 重试（好）               | 有空态（好） |

**用户影响**：慢网时用户会以为"项目没了/文档没了/需求没建成功"，可能重复创建或误报 Agent 未交付；失败时只有一行英文错误码、没有重试按钮，非技术用户只能手动刷新整页。`ui-foundations` §3.7 的硬性规则（"请求失败不能显示成空数据，也不能只弹 Toast"）在 12 个页面上未落地。

**改法**：给每页补 `listLoading`（骨架或 `role="status"` 的"正在加载…"）与 `PageState(kind)` 映射，失败用 `ErrorState(onRetry)`，已有旧数据时用 `PageState(kind:'stale')`；三个空态变体（no-data / no-match / waiting）区分开。工作台的实现可直接当模板复用。（S/页，合计 2–3 天）

### 2.3 【P1】信息架构与导航：12 个入口、没有面包屑、标题永远是 "WorkMesh"

**现象【事实】**

- 主导航 12 项分 4 组，组名用 `01/02/03/04` 编号；"需求 / 需求流水线 / 流程"三个近义词、`看板` 与 `流水线` 的分工需要读页面副标题才知道；没有导航搜索/命令面板，≤1440 的页面正文区里也没有任何"当前在哪个项目/需求"的面包屑。
- 所有页面标题都是 `<h2>`（0 个 `<h1>`），`document.title` 全站固定 `WorkMesh`（`index.html`；全仓 0 处 `document.title` 赋值）——浏览器开 5 个标签页无法区分，收藏/历史记录也是同一个名字。
- SPA 路由切换不复位滚动：从需求详情点"去签字"进入评审页，落点 `scrollY≈1659`（页高 2443），用户看到的是"仓库上下文"，评审对象/证据完整性在屏幕外；实测 `/knowledge` 滚到 900px 再点"需求"，落在 `scrollY=462` 的中段。`App.tsx:471-510` 无 `scrollTo`，也无焦点转移。
- 没有跳过链接（skip link），`main` 无 `tabIndex`；键盘用户从地址栏到正文需要 Tab 15 次以上。
- 页面级错误/成功提示出现的时机和位置不统一（顶部红字、右下 toast、`kb-notice` 绿字、页面级 ErrorState 四种并存，部分无 `role="status"`）。
- 项目上下文只在部分页面可见（工作台顶部有自己的"全部项目"下拉；需求/评审/看板/流水线/知识库/PRD/流程用 `ProjectSelect`；角色/ACL、设备授权、用户中心没有项目选择器，但操作又依赖项目）。项目页的行内"角色 / ACL""文档"跳转到全局页且不带项目 ID，多项目时会"看着 B 改 A"【推测：≥2 项目时】。

**用户影响**：新用户不知道 12 个入口的优先级；多标签页/深链接无法辨识；"我在哪个项目里看什么"要靠记忆；返回/跳转后总要从页面中段自己找位置。

**改法**

1. 每页 `<h1>` + `useDocumentTitle('需求 · WorkMesh')` + 路由变化 `scrollTo(0,0)`（同页 tab 不复位）+ 进入页面时聚焦 `main`（`tabIndex=-1`）+ 顶部 skip link。（S）
2. 页头增加面包屑/上下文行：`项目名（key）› 需求 › YFF-001 · 客户询价单`；项目选择器统一放到页头同一位置，未选择时明确提示"先选择项目"。（M）
3. 导航收敛：把"看板 / 需求流水线 / 流程"改名为"任务状态 / 需求进度 / 流程配置"等任务导向名称；给导航加 `⌘K` 搜索（可按需求编号/项目名跳转）。（M，可二期）
4. 通知中心变成真通知：深链到具体评审/变更、已读未读、按项目过滤（现状只有总数与最近活动）。（M，同源 usage-optimization P2，但页面层可直接落地深链）

**截图**：`d2-requirement-detail.png`（无面包屑）、`d3-review-decision.png`（滚动落点）、`m3-drawer.png`（12 项导航）

### 2.4 【P1】可读性：8.5–11.5px 的"审计事实"与 2.37:1 的对比度

**现象【事实】** 设计规范 `ui-foundations.md` §1.4 写的是"正文 ≥14px、次要信息 ≥12px"，实际 CSS 中字号字面量 373 处、其中 <12px 119 处（<10px 32 处，最小 7.5/8px）；页面实测每页 12–184 个 <12px 节点（看板 184、流水线 93、工作台 77）。对比度（WCAG AA 需 4.5:1）：

| 令牌/元素                            | 颜色 | 对比度 | 用在哪                           |
| ------------------------------------ | ---- | ------ | -------------------------------- |
| `--text-muted` #7b8aa0 on 白         | 3.51 | ✗      | 次要说明、表头、时间             |
| `--text-muted` on 页面底色 #f3f6fb   | 3.24 | ✗      | 大量辅助文字                     |
| `--accent` #0891b2 on 白             | 3.68 | ✗      | 链接/强调文本                    |
| 白字 on `--accent`（主按钮）         | 3.68 | ✗      | 登录/创建/确认主按钮             |
| `--success` #059669                  | 3.77 | ✗      | 状态标签                         |
| `--warning` #d97706                  | 3.19 | ✗      | 状态标签/警示                    |
| 工作台 `.rail-meta dt` 8.5px #94a3b8 | 2.37 | ✗✗     | SCOPE/PROJECTS/UPDATED、活动时间 |
| `.wb-row-context` 11.5px #7b8aa0     | 3.24 | ✗      | "YFF-001 · 客户询价单"           |

注意 **新令牌 `--wm-color-text-muted` / `--wm-color-accent` 与旧令牌同值**，所以"改用新组件"并不能自动达标；主按钮白字 3.68:1 是全局问题。承载"更新于/活动时间/谁在何时做了什么"的信息恰恰是这些低对比小字，而它们正是审批人判断"数据是否新鲜、能否信任"的依据。

**改法**：把 muted 文本统一到 `#64748b`（4.83:1）；强调文本用 `#0e7490`（5.36:1）；主按钮底色改 `#0e7490`（白字 4.9:1）；信息类小字一律 ≥12px，"SCOPE/SYS/UPDATED"这类装饰标签保留小字号但需 ≥3:1；在 `tokens.css` 与 `ui-v4.css` 一次性替换，避免双轨。（S + 回归 M）

### 2.5 【P1】视觉系统：4 层主题叠加、371 个色值、13 档 z-index

**现象【事实】** 样式由 `index.css(5040 行) → ui-v2 → ui-v3 → ui-v4` 四层覆盖加载，共 9 个 CSS 文件；颜色字面量去重 371 个、出现 961 次；`--bg-app/--surface/--border/--warning` 等 28 个变量在 4–5 个文件重复定义；存在两套令牌（旧 `--accent/--text-*` 与 `--wm-*`）；z-index 有 13 档（-2, -1, 0, 1, 2, 90, 95, 100, 120, 130, 160, 300, 400）；31 个 media query，断点从 520 到 1280 共 10 种，无统一栅格。

**用户影响**：同一语义在不同页面颜色/间距/字号不一致（"主按钮"在不同页有 3 种蓝），改一处颜色要追 4 个文件；新页面复用旧类名时外观不可预测；视觉噪声（网格底纹、扫描线、发光、渐变）让"证据/签字"这种严肃动作显得像演示大屏。

### 2.7 【P1】键盘与无障碍：做了 Modal，没做浮层

**现象【事实】**

- **通知中心**：Escape 不关闭（`App.tsx:153-163` 的 Esc 只处理 drawer/user menu）、点外部不关闭、打开后焦点仍在铃铛、Tab 直接进入背景内容；关闭后 `activeElement=null`。面板 `role="dialog"` 但没有 `aria-modal`。【事实，实测 1/1/1】
- **移动端导航抽屉**：无 `role`/`aria-modal`、无焦点陷阱（打开后 Tab 落到 logo）、关闭不回焦到汉堡按钮；而桌面端用的是同一套 `menu` 结构。相比之下 `Modal` 组件的焦点陷阱/Esc/遮罩/body 锁定/关闭回焦全部正常——说明能力已有，只是没复用。
- **页签**：需求详情/工作台共 10 个 `role="tab"` 缺 `aria-controls`/`role="tabpanel"`，不支持左右方向键，所有 tab 都在 Tab 序列里（应只 1 个）；工作台每条待办是 `article tabIndex=0` + 内部按钮，键盘用户每行要两次 Tab、读屏只读 article。
- **Modal**：`description` 未挂 `aria-describedby`；初始焦点落在"关闭"按钮（应落在第一个表单控件）；`ConfirmDialog` 的危险确认按钮仍是蓝色 `primary`（`tone='danger'` 在归档/吊销里大量未使用）。
- **动效**：`prefers-reduced-motion` 只覆盖部分 keyframes，drawer-in/toast-in/skeleton/task-state/pipeline-worker 未覆盖；1Hz 时钟会让整棵 App 每秒重渲染。
- **触控**：toast 关闭 20×20、流水线输入 19px、部分表格操作按钮 <24px。

**用户影响**：键盘重度用户（企业审批角色里比例不低）无法可靠关闭浮层、容易误触；读屏用户不知道"当前选中哪个 tab"；少量用户在"减少动态效果"系统设置下仍看到动画。

**改法**：通知中心直接复用 `Modal` 的图层栈与焦点逻辑（或抽出 `useDismissableLayer`）；移动抽屉改用已有 `Modal variant="drawer"`；页签补 `tabpanel/aria-controls` + roving tabIndex + 方向键；Modal 补 `aria-describedby`、初始焦点到第一个可编辑控件、危险按钮统一 `danger`；扩 reduced-motion 覆盖；时钟拆成独立组件避免整树重渲染。（S/M）

## 6. 做得好、别在"统一"时改坏

- **证据—摘要—票据主链路**：决定前给中文摘要、密码 + 一次性票据绑定动作/目标/版本/摘要，服务端二次校验。这是产品立身之本，优化应"减少点击/减少输密码次数"，不能放宽票据语义。
- **状态组件语义**：`PageState/EmptyState/ErrorState/StaleDataBanner` 把 loading/empty/no-match/no-access/waiting/stale 拆开，方向完全正确——问题只是采纳率低，应该大面积复用而不是重写。
- **Modal 实现**：焦点陷阱（Tab 循环）、图层栈（嵌套 Esc 只关顶层）、body 锁定、关闭回焦、遮罩关闭——实测全部正常，是全站最规范的部分；通知中心/移动抽屉应该复用它。
- **项目上下文 store**：loading/loaded/error/stale 状态机、并发去重、localStorage 只作记忆、失效回落——设计质量高。
- **看板"状态待确认"的诚实表达**：不把"服务端未返回执行状态"伪装成确定状态，符合平台"事实/证据"定位。
- **DiffViewer**：行号、折叠、逐处导航，桌面与 390px 均无横向溢出。
- **任意视口无页面级横向溢出**、**lucide 按需打包**、**路由级 lazy 拆分**、**焦点环可见**——这些基础都在。
