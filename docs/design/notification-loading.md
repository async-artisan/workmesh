# 通知面板按需加载

> 2026-11-10。P2 首页体积后续切片；工程方案不代替平台需求或 HUMAN 决定。本地执行结果见[验证记录](../testing/notification-loading-validation-2026-11-10.md)。

用户打开首页时应能立即看到准确的通知数字和工作台；只有打开通知面板才需要下载待办、活动列表和邮件摘要的展示代码。同源 r7 基线首页为 284,938 B raw，通知 r1 为 284,227 B，减少 711 B；gzip 估算增加 220 B。通知展示已按需加载，原 `<200000 B raw` 目标继续开放，仍需后续实际依赖优化。

保留 App 中的后台刷新、工作台快照、铃铛计数、按账号已读集合、跨标签页同步及通知 dialog 外壳。外壳立即提供标题、关闭、焦点进入、Tab 环绕和 Escape；内容由独立异步组件加载，慢请求及失败都可关闭，模块完成后不抢焦点。加载失败显示重试和刷新入口，关闭后迟到的下载不得重新打开。成功模块可缓存，失败清理自己的飞行请求；浏览器本身的失败缓存仍可能需要刷新恢复。

邮件发送的 busy/notice 状态继续属于 App，关闭再打开仍保留同账号发送进度与结果。发送绑定账号及请求代次，重复点击不得发出第二次请求，切换账号后旧结果不能回写新账号。关闭面板不撤销已发送到服务器的请求。既有待办、活动读取失败仍保留已知数据和显式重试。

选择保留常驻对话框外壳，是因为仅依赖 `notificationsOpen` 的现有焦点 effect 无法等待整个 lazy dialog 挂载；它还使慢加载阶段的键盘操作与正常面板一致。没有把数据读取移进条件挂载的内容组件，否则关闭面板会改变铃铛与后台更新语义。现有 WorkbenchDialogs 的显式加载/错误恢复方式可作为实现依据，不引入新的全站加载框架。
