# 托管 Agent 模式可行性分析（头脑风暴稿）

> 状态：**分析稿，不是承诺，不改变现行定位与路线**。写于 2026-11-04，对应一次「如果开一个新分支，不依赖本地 Agent，让大模型在系统里通过调用 API 完成全部功能，能不能做到」的讨论。
> 行号引用基于 2026-11-04 工作树（含当时未提交改动）；实现前须按关键符号复核。
> 方法：先拆问题，再对代码事实，再看开源参照，最后给判断与实验。事实与判断分开标注；`◻` 表示未逐条核验的外部信息。

---

## 0. 结论

**能做，但要做出来的是「另一件产品」——而且它不是一个产品，是四个可分开卖的东西。**

判断依据不在模型能力。2026-11 的模型能力、托管运行时、沙箱、持久执行、人工中断都已有成熟形态（§8）。真正决定成败的是三件事：

1. **生产能力**：平台现在只能接收外部生产的结果，不能自己生产。补这一层（沙箱 + 物料 + 编排 + 机器身份）是主体工作量（§3）。
2. **信任模型**：WorkMesh 的资产是「生产方 ≠ 裁决方」。平台自己生产后，摘要、快照、审计都从「独立见证」退化成「内部一致性日志」（§5）。
3. **定位与经济性**：目标客群画像与「不托管工作过程」边界是主动收窄的；平台侧执行是另一个更拥挤的品类，且要和客户已有的 Claude Code / Codex 包月正面比价（§7）。

### 0.1 一句话裁决

| 做法                                                               | 裁决                    | 理由                                                                                   |
| ------------------------------------------------------------------ | ----------------------- | -------------------------------------------------------------------------------------- |
| 平台全权生产全部角色交付（真 SaaS 全托管）                         | **no-go（现状定位下）** | 信任自证 + 定位冲突 + 经济反转 + 8–14 人月及持续运维；技术上不是不可能，是商业上不划算 |
| 平台把 Agent 侧能力协议化，让**任何**云端/客户侧 Agent 接入        | **go（推荐先做）**      | 工程最小、不改定位（`positioning.md` 已写「MCP 复用同一契约」）、直接验证需求          |
| 平台编排 + 执行留在**客户受控的 headless runner**                  | **go（推荐第二步）**    | 去掉「本地人」，不去掉「本地执行」；信任分离仍成立，且解决 CLI 断链痛点                |
| 平台只做独立验证（复算构建/测试、抓取并签名 CI、核验 PR↔需求锚点） | **go（可与上并行）**    | 保住分离，且 GitHub/Jira 都不做；是「有据可查」的硬增量                                |
| 平台托管**文档角色**（产品/UI/QA/运维）候选草稿                    | **go（最小切片）**      | 无沙箱、无 git，只需 LLM 循环 + 会话协议；用来验证「平台生产」的信任可接受性           |

### 0.2 「所有功能」必须先排除的东西

有些功能**不应该**被 API 化，否则这个产品就死了：

- 正式批准 / 撤销 / 发布 / 撤回 / 变更决定 / 流程实例化：必须 HUMAN Web 会话 + 一次性票据（§6.1 不变量 1、2）。
- 凭据授予与吊销：Agent 只能吊销自己，其余 HUMAN-only。
- 「产品采访」中的人：可以托管会话，但被采访的人必须是真的。

正确做法不是把 HUMAN 动作改成 API，而是把它变成**「Agent 可提议、人落槌」**：新增「提案」类端点（例如请求实例化、请求变更、请求澄清），保留落槌权在人。这比直接放开 HUMAN-only 端点安全得多，也更符合现有 `docs/positioning.md:73` 的「责任在人，执行在 Agent」。

## 1. 先把「本地 Agent」拆成四层

「依赖本地 Agent」是四个不同的依赖，混在一起讨论会得出错误结论：

| 层                | 现在谁提供                                                 | 能否搬到服务端         | 替代物                                                                | 难度                 |
| ----------------- | ---------------------------------------------------------- | ---------------------- | --------------------------------------------------------------------- | -------------------- |
| **L1 推理循环**   | 用户本机的 codex / claude-code（模型 + 工具调用循环）      | 能                     | LLM API（OpenAI / Anthropic / DeepSeek 兼容）+ 工具 schema            | 低                   |
| **L2 宿主脚手架** | 同一个本地二进制：工具集、上下文管理、重试、审批暂停       | 能，但**质量差距最大** | 买（OpenAI Agents SDK / Anthropic Managed Agents / Google ADK）或自研 | 高（自研）/ 中（买） |
| **L3 执行环境**   | 用户机器：仓库工作副本、shell、测试、`git commit/push`、PR | 能，但必须换成隔离沙箱 | E2B / OpenHands runtime / k8s agent-sandbox / 客户自托管 runner       | 中–高                |
| **L4 人类在场**   | 浏览器：设备授权、批准、产品采访                           | **不能也不应**         | 无（这就是产品）                                                      | —                    |

三条重要推论：

1. 现在真正「必须本地」的只有 **L3 的执行物料能力**（真实字节、sha256、commit）和 **L4 的人**。L1/L2 是可买可换的；`~/.workmesh` 凭据存放只是「目前放本地」（§3）。
2. 「不依赖本地 Agent」最省的实现是**把 L1+L2 交给别人的云端宿主**（Claude Code web、Codex cloud、OpenHands、客户自己的 runner），平台只把 L3/L4 的边界讲清楚。这正是候选形态 D。
3. 只要 L4 还在人手里，产品叙事就还成立；一旦平台既跑 L1–L3 又签发自己的证据，L4 的签字人就从「判断者」变成「背书者」（§5.1）。

## 2. 现状资产：为什么「API 化」本身是小事

这一点容易误判。WorkMesh 的 Agent 协议**已经完整 HTTP 化**，缺口不在「把 CLI 换成 HTTP」，而在平台没有生产能力。

| 已可原样复用                                                                                                               | 代码证据                                                                                                       | 对托管模式的意义                                                                           |
| -------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Agent 工作闭环全部端点：ready → claims → context-snapshots → resources → artifact-sets → review-requests → HUMAN decisions | `apps/api/src/tasks/*`、`apps/api/src/reviews/*`；`docs/api.md:148-159`                                        | 远端 Agent 不需要本地文件系统就能走完流程                                                  |
| 上下文快照是确定性、内容寻址的输入                                                                                         | `apps/api/src/tasks/v1-snapshot-policy.ts:7-36`；`v1-snapshot.service.ts:310-340`                              | 托管运行时天然拿到「不可变输入 + 可校验摘要」，比本地物化更干净                            |
| HOSTED 工件的真实字节**已在服务端**托管（`Artifact.bodyBytes`）                                                            | `apps/api/src/tasks/v1-artifact.service.ts:404-455`；`schema.prisma`（Artifact）                               | 「平台没有文件存储」是误判，只是缺「服务端算摘要 / 回读全文 / 大文件分片」                 |
| 角色包资源作为 `ROLE_RESOURCE` 进快照                                                                                      | `v1-snapshot.service.ts:324-340`；`v1-snapshot.controller.ts:81-94`                                            | **这是现成的「Agent 指令下发」通道**：SOP/skill 不用装到用户机器，平台可直接注入模型上下文 |
| 幂等键 + 版本 CAS + 追加式审计 + 一次性票据                                                                                | `v1-idempotency.ts`、`v1-confirmation.ts:106-205`、`schema.prisma`（AuditEvent/ReviewDecision/PrincipalStamp） | 长任务重试、审批中断恢复都有现成语义；托管模式不用另造一套                                 |

同时有三条**契约级硬约束**，是小改但必须改：

1. **物料由客户端声明**：`sha256`/`byteLength` 由 CLI 计算并声明，服务端只重算校验（`v1-task.controller.ts:86-90`、`v1-artifact.service.ts:427-441`）。纯 LLM 没有哈希工具时连正文都过不了。需要「服务端计算摘要」模式。
2. **`GIT_REF` 需要真实 commit**：40 位 SHA、`repoPath`、`projectRepositoryId` 全部由调用方给（`apps/cli/src/deliver.ts:189-222`；`v1-artifact.service.ts:458-527`）。没有仓库工作副本就无法产生。这是 L3 存在的根本原因。
3. **任务只能由 HUMAN 实例化流程产生**：`POST /requirements/:id/workflow-instances` 是 HUMAN-only（`v1-workflow.controller.ts:174-241`）。Agent 可以建需求，却生成不出可认领的任务——自治链在这里断。托管模式需要「Agent 提议实例化 + 人落槌」。

## 4. 四种候选形态

| 形态                         | 一句话                                                                      | 平台改动面                     | 上市时间 | 信任模型                       | 运维                             | 竞争位置                                                  |
| ---------------------------- | --------------------------------------------------------------------------- | ------------------------------ | -------- | ------------------------------ | -------------------------------- | --------------------------------------------------------- |
| **D 协议开放**               | 平台只暴露 Agent 侧能力（MCP/tool API + 机器身份 + 运行记录），宿主用别人的 | 小（G2、G6、G12）              | 3–4 周   | 不破坏：执行仍在平台外         | 无新增                           | 平台仍是「裁决层」，且变成任何 Agent 的接入层             |
| **A 独立验证者**             | 平台复算构建/测试、抓取并签名 CI、核验 PR↔需求锚点                          | 中（沙箱只读 + 代码证据扩容）  | 6–10 周  | **增强**：证据不再靠生产方自报 | 沙箱但只读、无外泄面             | GitHub/Jira 都不做；「有据可查」变硬                      |
| **B 编排 + 客户受控 runner** | 平台排任务、发上下文；执行在客户 VPC / 自托管容器里的 headless runner       | 中大（G1–G6、G12）             | 8–12 周  | 基本保持：执行主体仍是客户     | 1 个二进制/容器，客户运维        | 「去本地人，不去本地执行」                                |
| **C 平台全托管 SaaS**        | 平台既生产又裁决，对外卖「AI 交付即服务」                                   | 大（全部 + 多租户 + 安全运营） | 3–6 个月 | **被削弱**：需重建独立锚点     | 重（沙箱集群、出网、配额、值班） | 与 Claude Code web / Codex cloud / Jules / Devin 正面竞争 |

**推荐顺序：D →（文档角色 MVS）→ A/B 并行 → C 只在有付费证据后做，且换定位。**

理由：

- D 是把 `docs/positioning.md:36` 已经写下的「跨工具薄桥（CLI 一等公民，MCP 复用同一契约）」兑现，不是改定位。它直接回答用户的问题——**任何大模型/云端 Agent 都能通过 API 完成全部 Agent 侧功能**，只是不要求 WorkMesh 自己跑它。
- A 和 B 都不破坏「生产方 ≠ 裁决方」，还顺手补掉今天最弱的两个环节：CI 结果只存链接不验证（`docs/api.md:154` 自认「不抓取或验证」）、代码证据缺少需求锚点核验。
- C 的问题不是技术，是它把 WorkMesh 从「裁判」变成「既当运动员又当裁判」。若真要做，必须换品牌/换部署/换信任域，不能用现有产品的签字叙事。

## 5. 信任模型：生产方与裁决方分离怎么保

### 5.1 会塌什么（逐条）

| 不变量         | 现状锚点                                                                                  | 平台自产后                                      | 判定                                                               |
| -------------- | ----------------------------------------------------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------ |
| 字节/摘要可信  | 生产方在平台外算，平台重算校验（`v1-artifact.service.ts:427-441`）                        | 字节由平台自己的沙箱产生                        | **真塌**：摘要只证明「平台内部一致」                               |
| 输入不可变     | ContextSnapshot 内容寻址、摘要绑定                                                        | 仍成立（甚至可以更强）                          | 保持                                                               |
| 决定不可篡改   | 追加式 `ReviewDecision`/`AuditEvent`                                                      | 仍成立（只证明平台记录过什么）                  | 保持但不增值                                                       |
| 批准绑定版本   | 版本 CAS + 票据 binding                                                                   | 仍成立                                          | 保持                                                               |
| **独立生产**   | 唯一的平台外锚点：GitHub 代码证据（`v1-code-evidence-policy.ts:20-57`）+ 人复核的外部链接 | 代码只剩 GitHub；文档/设计/用例没有任何外部锚点 | **塌一半**，且文档类角色全塌                                       |
| 工作过程留本地 | `positioning.md:75-84` 明确不托管过程                                                     | prompt/工具调用/中间产物必然落在平台或沙箱      | 二难：存=违反边界且多一份风险资产；不存=比今天更难排障、更不可审计 |

### 5.2 证据分级（建议引入的新框架）

托管模式下，把所有「证据」按可独立验证的强度分级，签字权重按级别分配，而不是按平台自报：

| 级别 | 含义              | 例子                                            | 谁能造       |
| ---- | ----------------- | ----------------------------------------------- | ------------ |
| E0   | Agent 自报        | `checks[].source=AGENT_REPORTED`                | 任何 Agent   |
| E1   | 平台记录的运行    | AgentRun 事件、工具调用日志、token 账           | 平台（自证） |
| E2   | 第三方 CI 结果    | GitHub Actions / 客户 CI 的 run + commit SHA    | 代码托管方   |
| E3   | 外部人类评审/合并 | PR review by 非作者、merge commit               | 人           |
| E4   | **独立可复算**    | 任何人用 commit SHA + 密闭构建从零复现构建/测试 | 任何人       |

关键判断：**只有 E4 在「平台既生产又裁决」时仍然硬**。因为它的可信不来自平台签名，而来自「别人拿公开输入能重算出同样结果」。E1 再完整也只是自证；E2/E3 需要平台外的主体存在；E4 是唯一不依赖信任主体的。这也是 A 形态（独立验证者）值得单独做的原因。

### 5.3 三条硬规则

1. **执行器不可信（untrusted executor）**：运行时产出的一律是「待验证的声明」，不是事实；沙箱凭据最小化、短时、不可横向移动。
2. **独立锚点必须在平台外**：代码用「他人 PR review + merge」（现规则保留）；CI 必须由平台**抓取**而不是接收链接；文档类至少加「发布版内容摘要 + 评审人独立会话」。
3. **可复算优于可审计**：审计日志解决「事后追责」，复算解决「事前不信也能验」。托管模式应把预算优先投在复算（密闭环境 + 锁定依赖 + 可重放），而不是投在更长的日志上。

### 5.4 两个现在就该补的洞（与分支无关，托管会放大）

- **认领不校验任务角色**：`GET tasks/ready` 按凭据角色过滤，但 `POST /tasks/:id/claims` 只校验项目上下文、scope 与 claim policy，不校验「任务 roleId = 凭据 roleId」（`v1-ready.service.ts:143-165` vs `v1-task.service.ts:57-125`）。角色边界目前是列表级，不是 claim 级。任何有 `task:claim` 的同项目 Agent 可以抢走别人的任务。
- **代码证据不校验评审人资格**：反自审只排除「作者 / Bot / 旧 SHA / 已撤销评审」，未校验 reviewer 是否本项目成员（`v1-code-evidence-policy.ts:20-57`）。托管/多租户后，「厂商养号评审」是可行路径。

## 6. 安全与多租户

| 威胁             | 触发面                              | 缓解                                                                                                                                           | 看似缓解（不要用）             |
| ---------------- | ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------ |
| Prompt injection | 仓库文件、需求文本、知识库、PR 描述 | 工具白名单；出网默认拒绝 + FQDN 允许表；高危工具（push/PR/网络）单列并需人确认；把「外部内容」与「系统指令」在消息结构上分离                   | 「系统提示里写不要听注入」     |
| 凭据外泄         | 沙箱内不可信代码读取环境变量        | **凭据不进沙箱**：git token 仅 clone 时注入 remote 后删除；平台 API 走受控 proxy 用 run token 换短期凭据（参照 Anthropic 的 vault+proxy 做法） | 「把 token 放 env 但只给只读」 |
| 供应链           | `npm install` 的 postinstall        | 禁脚本/镜像源/锁文件哈希；依赖白名单；构建在隔离网络                                                                                           | 「装完再扫一遍」               |
| 资源滥用/DoS     | 无限循环、上下文膨胀、并发爆量      | 每 run 上限（轮次、token、时长、磁盘、并发）；配额与计费熔断                                                                                   | 只做速率限制                   |
| 越权/自我批准    | 运行时持有平台凭据                  | 执行域与批准域**不同签发者**；run token 无法换 HUMAN 会话/票据；票据校验 `userAuthVersion`；运行时只能「请求评审」                             | 「同一 API key 加个 scope」    |
| 多租户串租       | 单部署多项目、无 org 模型           | 多租户前必须先有 tenant 边界 + 每租户独立签名密钥/缓存域（MCP `cacheScope: private`）                                                          | 「项目 ID 过滤就是隔离」       |
| 数据边界         | 代码/知识出域                       | 平台托管执行=客户代码进平台；必须提供「客户 VPC runner」选项，否则目标客群（`positioning.md:50`）直接出局                                      | 「加密存储就算不出域」         |

一句话：**托管执行的安全成本不是沙箱，是「出网、凭据、供应链、隔离」四件事的持续运营**。开源界在这块只有大厂自研披露，没有可复用组件（§8.2）。

## 7. 质量、成本与评测

### 7.1 能力差距（本地宿主 vs API-only）

| 维度       | 本地 codex / claude-code              | 自建 API 运行时                              | 影响                           |
| ---------- | ------------------------------------- | -------------------------------------------- | ------------------------------ |
| 工具       | 成熟（读写/搜索/shell/补丁/子 Agent） | 要自己造或买                                 | 最大差距项，不是模型           |
| 上下文管理 | 压缩、缓存、子会话                    | 要自己实现                                   | 长任务膨胀会直接吃掉质量       |
| 迭代次数   | 高（用户可中断）                      | 受成本/超时约束                              | 难任务失败率上升               |
| 环境       | 用户真实环境（真实依赖、真实数据）    | 沙箱需复刻（环境一致性是第二硬问题，见 7.2） | 本地能跑、沙箱跑不了           |
| 模型       | 用户订阅的最新模型                    | 你选的模型/版本                              | 可通过「允许客户自带 key」缓解 |

结论：**API-only 与本地宿主的差距主要在脚手架，不在模型**。所以「买 harness、留裁决」比自己造 agent loop 更划算（§8）。

### 7.2 环境一致性 > token 成本

托管执行最先崩的不是账单，是「同一仓库在沙箱里装不出依赖 / 测试跑不过 / 版本漂移」。缓解：DevContainer / Nix / 锁定镜像 + 依赖缓存；把「环境能否复现」做成每个 run 的显式检查项，失败即 `NEEDS_CLARIFY`，而不是让 Agent 猜。这也是 A 形态（复算验证）的副产品价值。

### 7.3 成本量级（假设，非报价）

假设：输入 $1–3/M tokens，输出 $10–15/M tokens，缓存命中率 60–80%，中位代码任务 50–150 轮工具调用。

| 任务类型                           | 上下文/输出量级              | 单任务成本   | 与客户现有包月对比                      |
| ---------------------------------- | ---------------------------- | ------------ | --------------------------------------- |
| 文档角色（PRD/设计/用例/发布说明） | 50–150k 输入、10–30k 输出    | **$0.2–1.5** | 明显便宜，值得优先托管                  |
| 中位代码任务                       | 2–8M 累积输入、0.2–0.5M 输出 | **$4–15**    | 与 Claude Code/Codex 包月同量级甚至更贵 |
| 困难代码任务                       | 10–30M 累积输入、1–2M 输出   | **$20–60**   | 单任务成本超过多数团队人均月费          |

含义：**按任务计价卖「交付」比卖「工具」更合理**；否则客户会问「我已有订阅，为什么还要为你跑同一件事付 token」。文档角色是最健康的第一切片。

### 7.4 如何证明质量不降（四个可执行实验，2–4 周）

1. **历史回放（最高性价比，用自己的数据）**：从现有数据库里取已验收交付（任务 + 快照 + 工件 + 人工决定）做 golden set，让托管运行时重做，对比「人工会不会批准」。指标：一致率、返修理由分布。这是唯一直接回答「在我们客户仓库上掉不掉质量」的证据。
2. **同脚手架 A/B**：固定模型、prompt、工具集、迭代上限、超时，只换执行位置（本地宿主 vs 平台沙箱），20–50 个已合并真实任务。阈值建议：质量差 ≤10pp、成本 ≤1.25×，否则不进下一步。
3. **公开基准确认外部锚点**：SWE-bench Verified 已饱和（>70%），只能防退化；用 SWE-bench Pro 的 held-out 子集 + Terminal-Bench 自行重跑（旧分数不可引用）。
4. **红队**：注入（仓库/PR/需求/知识库）→ 测外泄、越权、自我批准；要求零成功，失败即修，不进入下一阶段。

### 8.2 开源界还没有好答案的三件事（本次调研最重要的结论）

1. **「执行证据」的可信度没有标准**。所有方案都在解决「怎么把 agent 跑起来」，没有一个解决「跑起来这件事怎么让第三方相信」。session 日志由生产方自写=自证；OTel trace 是观测不是证据（可篡改、规范未冻结）；SLSA/in-toto 签得了构建产物，签不了「agent 在这台沙箱里做过这次判断」（是否已扩展到 agent 运行未核验 ◻）。唯一接近的实践是把执行放到第三方基础设施（GitHub Actions / 客户 VPC runner），让**基础设施方**提供独立日志——这要求平台承认自己不是执行方。
2. **多租户 + 不可信代码 + 凭据隔离**只有大厂内部实现。出网控制依赖单云私有能力，跨云无统一做法；中小团队自建成本被严重低估。
3. **「质量不降」没有可比口径**。Verified 饱和、Pro 强依赖 scaffold、Terminal-Bench 版本口径混乱；没有一个基准回答「同模型换执行位置后差多少」。这个只能自己做（§7.4），也恰是最有价值的对外证据。

## 9. 建议路线（每阶段都有退出条件）

| 阶段                | 内容                                                                                                      | 时间盒   | 退出条件（不满足就停/改）                                                      |
| ------------------- | --------------------------------------------------------------------------------------------------------- | -------- | ------------------------------------------------------------------------------ |
| **P0 决策实验**     | ①历史回放评测（§7.4-1）；②红队注入；③「第三方可复算」演练（给外部工程师 commit+工件，看能否独立验证）     | 2–3 周   | 回放一致率 ≥80% 且红队零成功，才继续                                           |
| **P1 形态 D**       | MCP server（白名单工具）+ 机器身份（工作负载 token / client credentials）+ AgentRun 记录 + 服务端摘要模式 | 3–4 周   | 一个外部云端 Agent（或第二个宿主）能不用 CLI 走完 claim→context→deliver→review |
| **P2 文档角色 MVS** | 托管产品/文档 Agent：会话 API（G9）+ LLM 循环 + 工具 + 运行记录；只产候选，人批准                         | 4–6 周   | 3 个真实团队愿意用它的 PRD 候选；信任问卷不出现「平台自证」质疑                |
| **P3 形态 B/A**     | 客户受控 headless runner（容器/二进制）+ 独立验证（复算构建、抓取 CI、PR 锚点）                           | 8–12 周  | 环境一致性 ≥95%、质量差 ≤10pp、成本 ≤1.25×                                     |
| **P4 形态 C**       | 平台全托管 SaaS（多租户、沙箱集群、配额、值班）                                                           | 3–6 个月 | 有付费客户 + 独立证据链（E2–E4）跑通 + 换品牌/换信任域                         |

### 9.1 三个必须先验证的假设

- **H1 信任可接受性**：客户是否接受「平台生产 + 平台存证 + 平台复算」？实验：拿两种证据包（自证 vs 可复算）给 5 个目标客户做选择，看他们是否追问「我怎么信你」。
- **H2 质量与成本对等**：同 scaffold 换执行位置，代码任务质量是否掉 ≤10pp、成本是否 ≤1.25×。
- **H3 需求真实**：愿意为「不用装任何东西、在浏览器里把一条需求走到签字」付钱的人，是否比「已经装好 Codex/Claude Code 的人」更多？这是整个分支的存在理由。

## 10. 工程与分支策略

**推荐同 repo 加包，不 fork**：

- 新包 `apps/agent-runtime`（或 `packages/agent-runtime`）+ 新增表（`AgentRun`、`AgentRunEvent`、`AgentToolCall`、`SandboxLease`、`ReplayVerification`、`ExecutorIdentity`），全部**只加不改**现有表。
- **dogfood 规则（关键约束）**：运行时必须是**纯公开 API 客户端**——不 import `apps/api` 内部代码、不直连数据库。这样运行时的完整性等价于 API 的完整性，也保住「以后把运行时拆出去」的自由。
- 契约放 `packages/shared` 并版本化；执行器能力面放进 `spec/`，与角色包 manifest 分开（角色包是「规范」，执行器是「能力」）。
- 若确需独立 repo：先抽 `packages/shared` 为独立包并发布，否则两个 repo 的协议必然漂移。MIT 基线不要引 BUSL 组件（Restate）。

**不可动清单**（无论哪个形态）：

- HUMAN-only 守卫与一次性票据（这是账本，不是障碍）；
- `expectedVersion` + `Idempotency-Key` + `INVALIDATED` 语义（删掉等于放弃「签字会过期」）；
- 「代码证据必须来自他人评审、Bot 无效、SHA 必须等于 PR head」——平台自己提交代码时，这条需要**新的第三方锚点**（E2/E4），否则自动失效。

## 11. 未决问题（需要拍板）

1. **「不依赖本地 Agent」你指的是哪一层？** 不装本地工具（D）、不要本地人（B）、还是平台全托管（C）？三者工程差 10 倍以上。
2. **是否接受「平台既生产又裁决」？** 若接受，是否愿意为新分支换品牌/换信任域（否则现有「有据可查」叙事会被稀释）。
3. **代码/知识能否出域？** 若不能，C 直接排除，只剩 B（客户 VPC runner）与 D。
4. **商业形态**：卖座位、卖任务、还是卖「可复算的验收报告」？定价决定做哪个形态。
5. **谁来运维沙箱？** 平台团队现在是否有人力承担 0.5–1 FTE 的持续运维与值班。
6. **「所有功能」是否包含 HUMAN 动作？** 我的建议：不包含，改成「Agent 可提议、人落槌」。
