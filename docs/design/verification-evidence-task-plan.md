# 交付验证与评审体验任务计划书

> 编制日期：2026-11-12。状态：按依赖实施中。本文承接 MissionControl 对照分析；任务编号只用于实施分工，不是平台需求编号、批准记录或新的状态源。实际改动、行为证据及未执行项持续记录在[本轮实施记录](../testing/verification-evidence-validation-2026-11-12.md)。用户已确认暂无隔离 GitHub 环境，真实外部闭环保持 NOT_RUN，不能据本地实现宣称 M3/M4 验收完成。

## 1. 用户结果与产品边界

让交付者清楚知道需要补什么证据，让 QA 能追溯实际执行的用例版本，让评审人在同一页面看清当前交付的依据、异常和可作出的正式决定。

预期形成四个可独立交付的结果：

1. **评审可理解**：资料是否读全、版本是否匹配、报告是否通过、代码评审是否满足、是否等待人工签字分别说明。
2. **执行可追溯**：验收 key、具体用例及修订、执行记录与交付版本直接关联。
3. **外部验证有来源**：平台能从一种受信 CI 提供方核对运行事实，区分 Agent 自报、普通外部引用和已核对的提供方事实。
4. **变化可恢复**：需求、代码、用例或验证定义变化后，解释旧证据的适用范围与下一步，不覆盖历史事实。

成员和本机 Agent 继续负责调查、实现和提交；CI、测试平台与 QA 负责执行验证；WorkMesh 负责事实、权限、版本、证据关联、流程约束与 HUMAN 正式决定。平台本轮不运行 Agent、不触发或重跑 CI、不维护 Runner/沙箱、不自动修复、合并或部署。

规则继续通过现有需求/变更、工作流修订、已发布 KNOWLEDGE、角色 required 绑定与上下文快照生效。本文不新增 constitution、审批文件或独立批准状态。新增硬门禁必须先进入现有正式流程的版本与变更机制，不能靠前端判断悄悄改变在途实例。

## 4. 目标证据关系与信任边界

目标关系为：**正式验收 key → 具体用例与修订 → 执行结果 → 提供方 run/attempt/job/报告 → 当前交付**。各层保存其来源，不允许由上传方自填一个 `verified: true` 获得平台权威。

| 层次           | 必须说明的内容                                                              | 不能据此推导                                             |
| -------------- | --------------------------------------------------------------------------- | -------------------------------------------------------- |
| 本地报告       | 报告者、验收、用例修订、PRD/快照/完整代码 SHA、声称结果与引用               | 程序已见证执行、平台已批准                               |
| 提供方运行事实 | 登记仓库的 provider ID、run ID、attempt、job ID、原始状态、采集时间与范围   | 报告内容诚实、测试足够或定义独立                         |
| 报告关联       | artifact ID、字节摘要、对应 run/attempt、用例结果、解析完整性，job 关联依据 | 同名文件就是同一次执行、报告中的业务结论已经被第三方证明 |
| 验证定义       | 工作流、测试集合、断言及必要配置的准确版本、已批准依据和候选改动            | 运行在不同进程或 GitHub 托管 Runner 就自然独立           |
| 当前适用性     | 当前工件/提交、PRD、快照、代次、用例修订、规则版本与证据的关系              | 历史通过永远有效、采集时成立就代表之后实时成立           |
| HUMAN 决定     | 原决定主体、对象、版本、槽位、票据与审计                                    | 机器通过等于人工批准、ACK 等于修复完成                   |

### 4.1 用例修订与报告格式建议

- 用例新增精确修订引用和内容摘要，优先指向既有不可变 CASES 工件及其摘要；本地分析只能检查输入一致性，服务端关联时再核对实际工件与权限。不新增独立用例审批系统。
- `evidence` 直接关联非空用例引用；引用必须属于包内/正式工件中的用例且验收关系、verification 一致。报告中的 runId 是关联描述，不能自行获得来源确认。
- 拟议 CI JSON 结果报告显式记录 schemaVersion、提供方运行关联、被测代码、用例 ID/修订、实际结果和环境摘要。提供方身份由服务端事实核对，报告字段视为不可信输入。
- 1.0 报告仍可读取，明确显示“未建立执行到用例修订的精确关联”；不得为它虚构 revision 或独立 CI 来源。不能仅将旧包的 schemaVersion 改成 1.1。
- `LOCAL_REPORTED`、`REPORTED_PASS` 与已核对的提供方运行事实分别展示；禁止给本地 quality 工具增加联网或实际运行测试的隐含行为。

### 4.2 首轮 GitHub Actions 的支持范围

- 首个真实闭环只验收登记隔离仓库中、精确提交触发的受控 `push` 工作流、完整一次 attempt 及一种 JSON 报告。其他事件可以保留提供方事实，但没有证明实际被测代码时不建立当前有效绑定。
- `run.head_sha`、PR head 和实际 checkout SHA 分开记录。`pull_request` 的合并引用、`pull_request_target`、`workflow_run` 等不能直接套用 `push` 规则。缺少可靠被测代码关联时返回未知。
- 首轮不合并不同 attempts 的 job 结果。部分重跑无法证明完整执行时显示不完整，提示在 GitHub 执行完整运行；WorkMesh 不触发重跑。
- 报告与指定 attempt/job 的关联必须有可核对依据；provider 未给出充分关联且只有文件名或时间推测时保留未知，不能因 artifact 名称相同而拼接。
- 受控工作流从已发布并进入快照的验证要求取得必需 jobs、用例集合及规则依据；候选修改工作流、断言、测试配置或依赖时单独诊断，不自动声明定义独立。可展示不同维度，不输出含糊的单一绿灯。
- 首轮只读同步保留采集完整性和时间；关键绑定前再读取并校验目标身份，读取期间上游变化则不提交有效绑定。后续是否用于硬门禁及其实时性要求另行设计。

### 6.1 共享文件协调与并行顺序

1. EV-00 后前端做 EV-01，后端可做 EV-05 调查与契约；先固定摘要语义，再让 EV-03 使用相同状态定义。
2. `ReviewDecision.tsx` 按 EV-01 → EV-02 → EV-06 → EV-09 → EV-11 串行交接；EV-04 若修改同文件，排在 EV-02 后。组件独立文件可在契约稳定后并行。
3. `quality.ts`、shared 导出与契约样例由 EV-05 单一负责人先定稿，EV-06 再同步调用方；EV-07 不另造第二套用例版本含义。
4. `schema.prisma` 与迁移由 EV-07 单一负责人维护。迁移序号实施时重新枚举，不预占编号、不改既有迁移字节；适配器可在存储契约稳定后并行。
5. `apps/web/src/api/resources.ts` 的 F2/F5 类型按契约版本顺序合入。EV-09/EV-10 共用绑定与诊断模块，由同一后端负责人协调，不并行修改正式验收主事务。
6. 角色资源与生成文件只在 EV-06 集中生成；实施中发现额外调用方时追加映射和验证，不覆盖已锁定版本。

### 8.1 执行入口

- 文档与格式：针对实际改动文件运行 Prettier；本计划编制只检查 Markdown，不运行无关产品测试。
- 实施时先运行受影响包的定向测试、类型检查和构建：`pnpm --filter @workmesh/shared ...`、`@workmesh/cli`、`@workmesh/api`、`@workmesh/web` 与实际受影响的角色包；具体测试文件随任务用例固定，禁止只执行镜像实现的浅层断言。
- shared/API/错误码/生成资源变化运行 `pnpm test:contracts`；角色包使用 `pnpm --filter @workmesh/role-packages generate`，随后运行该包测试与构建。
- 持久化、并发、权限、绑定与正式验收使用显式隔离 PostgreSQL，执行迁移、漂移、回滚/恢复适用性检查和对应集成入口。禁止 `db push` 消除漂移，不改写已应用迁移。
- Web 交互执行受影响组件测试和 `pnpm test:browser`；数据库和浏览器均使用隔离环境，覆盖键盘、焦点、可访问名称、错误与重试；mock 只证明受控展示，不替代真实端到端。
- 最终候选执行完整 `pnpm verify`；首次迁移仅在测试目标已核实且适用时使用现有 `--apply-migrations` 入口。记录最终 source SHA/工作树清单、远端同提交 CI、报告与制品摘要。
- 有真实 PRD、需求、快照和任务映射后，按已实现版本运行 `workmesh quality --file <JSON> --json` 检查本地一致性。本次无正式 PRD/快照，不伪造 ID、不生成假质量包；其 CONSISTENT 也不代替行为验证或 HUMAN 决定。

### 8.2 外部真实闭环

EV-00 明确可用的隔离 GitHub 仓库、登记 provider repository ID、只读凭据权限、受控 workflow 及保留策略；凭据不入库、不出现在日志或报告。EV-08/EV-12 使用经授权的目标产生真实成功、失败和完整重跑记录，核对 run/attempt/job/artifact 与交付代码。

没有外部目标或权限时，继续完成 mock、契约、隔离数据库和 UI 可做的任务；真实闭环明确保持 BLOCKED/NOT_RUN，M3/M4 不能宣称完成。既有 GitHub 人工 PR review 的 live 待验证项也不能被新的 Actions 样本替代。

## 9. 异常、数据演进与回退

| 异常或风险                                 | 必须保留的行为                                                                                                                        |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| 外部 403/404、撤权、限流、超时或分页不全   | 返回可解释的未知/不完整及恢复动作；403/404 不自动等于不存在；保留上次采集时间且标明过期，不用旧 PASS 冒充新结果                       |
| provider success 与逐条报告冲突            | 两者同时保留，必需项异常可见；重复 PASS 不掩盖失败；报告缺失不推断零失败                                                              |
| 候选自带报告、伪造 checkout 或更改验证定义 | 报告始终作为内容声明；来源确认与定义独立性分别判断，证据不足保留未知                                                                  |
| 下载报告存在重定向、压缩包或超大输入       | 只从适配器核对的提供方资源读取；受限超时/大小/展开量/条目数，防路径穿越，不执行下载内容，不向非允许目的地转发凭据                     |
| 相同身份冲突内容、重复请求或乱序状态       | 保留不可变原事实与冲突诊断；不覆盖 completed 为旧 queued；重跑使用新 attempt，成功重跑不删旧失败                                      |
| 代码、基线或角色包版本在途改变             | 沿用现有失效/恢复和角色版本锁；对实际读取的版本复核，禁止自动接受最新版本                                                             |
| 验证存储或外部提供方不可用                 | 新证据显示未知，保留原人工评审链与既有硬门禁；不全局关闭原门禁，也不靠新提示新增隐含阻断                                              |
| 新质量包或新表回退                         | 新表采用增量迁移，保留旧字段/历史；旧版不理解新包时明确不支持。使用已验收旧制品与已验证兼容分支，不能把 1.1 字节改标 1.0 或删除新事实 |

迁移实施前列明候选版本、备份目标、旧应用兼容性和停用新接入的方式。在隔离库验证新旧数据读取与恢复；若旧应用不兼容新结构或存在不可逆数据变化，恢复到新的隔离实例并由恢复负责人按现有发布流程决定切换，不自动回删表或覆盖工作库。
