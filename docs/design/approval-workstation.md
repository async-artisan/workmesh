# 审批工位设计

> 状态：证据卡已实现；批处理、委托、超时升级为设计稿。日期：2026-11-03。
> 目标：把 Web 从「数据后台」变成「人关门的地方」——待办优先、一屏证据、一门一动作。

## 1. 现状盘点

工作台（`/`）已经具备：

| 能力       | 实现                                                         |
| ---------- | ------------------------------------------------------------ |
| 待办聚合   | 待签字、待审批、待确认变更、可开工任务，统一计数             |
| 排序与筛选 | 按类型/项目/时间；按角色过滤；`localStorage` 记住角色偏好    |
| 证据卡     | 工件数、类型、是否含 PR、代码引用数、检查通过数、年龄        |
| 决定       | 抽屉内完成，复用 `ReviewDecision` 页面与票据校验，不另造权限 |
| 变更确认   | 抽屉内确认收件人版本，409 原样展示                           |
| 邮件摘要   | 服务端聚合待办数与链接                                       |

证据卡字段（本次补齐）：

```ts
evidence: {
  artifactCount: number;
  artifactKinds: string[];      // PRD / DESIGN / IMPL / CASES / RELEASE
  hasPr: boolean;
  codeRefs: number;             // 带 commitSha 的工件数
  checks: { total: number; failed: number };
}
```

界面按「证据 3 件（IMPL / CASES）· 含 PR · 代码引用 2 · 检查 11/12（1 失败）· v3」展示。旧服务端响应缺字段时按空值降级，避免滚动发布期间白屏。

## 2. 还缺什么

| 缺口      | 影响                             | 建议优先级  |
| --------- | -------------------------------- | ----------- |
| 批处理    | 一次只能批一条，评审排队         | P1          |
| 委托      | 审批人休假/不在，流程卡死        | P2          |
| 超时升级  | 等人拍板没有时限与升级           | P2          |
| 风险分级  | 所有条目同等对待，低风险也要全审 | P2          |
| 验收覆盖  | 看不到「这条决定覆盖哪几条验收」 | 依赖迁移 M2 |
| 变更 diff | 只看到改了哪些字段，看不到前后值 | P3          |

## 3. 批处理

**规则**

1. 只允许同一项目、同一评审类型（`TASK_ACCEPTANCE` 或 `RELEASE_ACCEPTANCE`）一起批。
2. 每条独立校验 `expectedVersion`，**不允许全有或全无**——部分成功要明确返回每条结果。
3. 每条仍需一次性确认票据；批量票据绑定「条目集合 + 各自版本 + 摘要」。
4. 高风险条目（`criticality: HIGH` 或 `checks.failed > 0`）不允许进批量，必须单独看。

**接口草案**

```
POST /api/v1/review-requests/batch-decisions
{
  "decision": "APPROVE",
  "items": [{ "reviewId": "...", "expectedVersion": 3, "confirmation": {...} }]
}
→ { "results": [{ "reviewId": "...", "status": "APPLIED" | "CONFLICT" | "FORBIDDEN" }] }
```

**为什么不做「一键全批」**：审批的价值在「看一眼」，全批会把工位变成橡皮章。

## 4. 委托

**规则**

1. 委托是**槽位级**的临时记录：`delegatorUserId → delegateUserId`，带 `expiresAt`，到期自动失效。
2. 原 `requiredUserId` 不变，审计里同时记录委托人与被委托人。
3. 只能委托给具备该审批资格的人（同角色或管理员）。
4. 高风险槽位禁止委托。

**成熟参照**：GitHub 的 team mention / CODEOWNERS 不能真正替代审批，Gerrit 的 reviewer 替换保留了投票历史——委托应追加记录，不覆盖原责任人。

## 5. 超时升级

**规则**

1. 每个审批槽有 `dueAt`（按风险分级：HIGH 24h、MEDIUM 72h、LOW 7d）。
2. 到期未决定：先提醒责任人，再升级到角色负责人，最后升级到项目 owner。
3. 升级只发通知与加徽标，**不自动批准**。
4. 工位按「超期时长」排序置顶。

**成熟参照**：PagerDuty / Grafana OnCall 的升级策略——升级是「换人看」，不是「自动放行」。

## 6. 风险分级与抽样

- 依赖验收的 `criticality`（迁移 M2）与 `checks.failed`。
- 低风险 + 全部检查通过 + 有代码证据 → 允许「快速批准」，但仍在审计里记一笔。
- 高风险或检查失败 → 强制打开证据卡，且不允许批量。

## 7. 验收覆盖

迁移 M2 之后，任务带 `acceptanceKeys`，工位应展示：

```
覆盖验收：A1 ✓  A2 ✓  A3 未覆盖（缺证据）
```

未覆盖的验收必须阻断批准，或要求填写豁免理由。

## 8. 变更 diff

`ChangeEvent.changedFields` 只说明改了哪些字段。要看前后值，需要：

1. 变更单 `ChangeRequest.diff` 结构化（迁移 M3）；
2. 工位渲染 diff 视图，默认折叠，只展开被改条目。

## 9. 推荐落地顺序

1. **P0（已完成）**：证据卡字段与降级。
2. **P1**：批处理（同类型、逐条校验、部分成功）。
3. **P2**：委托与超时升级（依赖槽位 `dueAt`，排在迁移 M3 之后）。
4. **P2**：风险分级（依赖 M2 的 `criticality`）。
5. **P3**：变更 diff（依赖 M3 的 `ChangeRequest.diff`）。

## 10. 与其它设计的关系

- 审批动作仍只走服务端票据与版本校验，前端不新增权限路径。
- 变更确认复用 `change-recipients`，不新造通知表。
- 批处理与委托都必须写审计，审计是工位的底线。
