> 状态：证据卡、批量决定、槽位委托和手动超时升级已实现。浏览器闭环及其他验证状态以 [阶段状态](../phase-status.md) 为准。更新日期：2026-11-04。
> 目标：把 Web 从「数据后台」变成「人关门的地方」——待办优先、一屏证据、一门一动作。

## 3. 批处理（已实现）

**当前接口行为**

1. HUMAN Web 会话提交统一决定，每批 1–20 条；各条提供 `reviewId`、`slotId`、`expectedVersion` 和自己的确认票据。
2. 每条独立执行权限、版本与一次性票据校验，返回 `APPLIED` 或对应错误码；部分失败不回滚已成功条目。
3. 没有整批共用的确认票据；已消费票据不能通过重新提交整批来复用。操作时可以按项目和评审类型分批查看，服务端仍逐条授权。
4. 按 `criticality` 或失败检查强制排除批量属于后续风险分级设计，不能当作当前已执行的门禁。

接口使用清单见 [API 文档](../api.md)。请求形态如下：

```json
{
  "decision": "APPROVE",
  "items": [
    {
      "reviewId": "<uuid>",
      "slotId": "<uuid>",
      "expectedVersion": 3,
      "confirmation": { "ticketId": "<uuid>", "ticketSecret": "<secret>" }
    }
  ]
}
```

## 4. 委托（已实现）

OWNER/ADMIN 可为审批槽创建临时委托，目标必须是当前项目有效成员，`expiresAt` 必须晚于当前时间。同一槽位只允许一条有效委托；原 `requiredUserId` 保留，到期或撤销后委托失效。

同角色资格限制已实现：槽位绑定业务角色（`requiredRoleId`）时，被委托人必须持有该角色的有效 assignment，否则返回 422 `DELEGATE_ROLE_MISMATCH`。高风险槽位禁止委托与更细的委托审计展示仍需单独设计和核验。

Web 端在评审页「委托 / 超时」视图提供创建/撤销与到期提醒：24 小时内到期的生效委托显示提醒横幅与「即将到期（N 小时）」状态。

## 5. 超时升级（手动触发已实现）

成员可读取到期且未决定的审批槽，结果按 `dueAt` 排序；OWNER/ADMIN 可调用升级接口，对到期、未决定且尚未升级的槽位写入 `escalatedAt`。升级不会自动批准。

工作台已置顶逾期审批：`/workbench` 返回跨项目 `overdueApprovals`（按 `dueAt` 升序、含逾期时长与是否已升级），点击可直接进入对应评审。截止时间按风险自动分配、定时调度与多层自动提醒仍是后续目标。

## 6. 风险分级与抽样（后续设计）

- 依赖验收的 `criticality`（迁移 M2）与 `checks.failed`。
- 低风险 + 全部检查通过 + 有代码证据 → 允许「快速批准」，但仍在审计里记一笔。
- 高风险或检查失败 → 强制打开证据卡，且不允许批量。

## 7. 验收覆盖（后续设计）

任务已经有 `acceptanceKeys`；工位的逐项证据覆盖与豁免展示仍需设计，例如：

```
覆盖验收：A1 ✓  A2 ✓  A3 未覆盖（缺证据）
```

未覆盖的验收必须阻断批准，或要求填写豁免理由。

## 8. 变更 diff（后续设计）

`ChangeEvent.changedFields` 只说明改了哪些字段。要看前后值，需要：

1. 核对既有 `ChangeRequest.diff` 的字段结构与实际读取接口；
2. 工位渲染 diff 视图，默认折叠，只展开被改条目。

## 9. 后续完善顺序

1. **已实现**：证据卡、批量决定、槽位委托和手动超时升级。
2. **后续设计**：风险分级与验收覆盖，需结合当前数据模型和阶段状态重新确认依赖。
3. **后续设计**：结构化变更 diff；具体范围和迁移依赖以当前开发计划为准。

## 10. 与其它设计的关系

- 审批动作仍只走服务端票据与版本校验，前端不新增权限路径。
- 变更确认复用 `change-recipients`，不新造通知表。
- 批处理与委托都必须写审计，审计是工位的底线。
