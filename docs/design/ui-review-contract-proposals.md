# 页面审查：邀请发现与流程步骤名称的契约及结项记录

本文件以本轮用户确认的范围为准。#15 的邀请发现仍是后续方案；#29 的可选步骤名称已实现。两者不能混为同一交付状态。

## #15 当前用户待处理邀请

### 已有能力与边界

`ProjectInvitation` 保存 token 的哈希、可选邮箱、角色、有效期、接受与撤销状态；明文 token 在创建时返回，管理员按项目查看待处理邀请的列表不返回 token。现有 `/invite/:token` 使用 token 解析并接受邀请，服务端重新校验邀请状态、账号及可选邮箱，并以事务和条件更新防止重复接受。无邮箱绑定的邀请以持有链接为凭据。`User` 当前没有邮箱验证状态，不能把账号邮箱相同当作已验证邮箱。

### 供评审的最小方案

1. 明确账号与邀请的安全绑定。推荐先建立可证明的收件人身份（例如已验证邮箱，或创建邀请时明确绑定的用户 ID），再开放无需 token 的发现和接受。仅匹配当前未验证的账号邮箱是较小的改动，但其冒领与信息泄露风险需要产品及安全负责人明确接受；不能允许客户端提供任意邮箱查询。
2. 可考虑新增 `GET /v1/me/invitations?status=pending`：只从已认证的当前用户推导收件人，分页返回必要的邀请 ID、项目显示信息、角色和有效期，不返回 token、token 哈希或其他收件人信息。待处理集合只包括未接受、未撤销且尚未过期的邀请；归档项目建议排除或明确标记不可接受，产品需选择。列表和接受都应由服务端重新校验，不能信任前端筛选。
3. 可考虑新增 `POST /v1/me/invitations/:id/accept`：使用同一身份绑定校验，在事务内复用现有状态、项目可用性、账号、角色和一次性 CAS 检查；并发接受、撤销或过期时返回可操作的稳定错误。不得借邀请 ID 绕过收件人验证。原 `/invite/:token` 和匿名注册/接受流程保持兼容。
4. 未绑定收件人的链接邀请继续通过管理员发送链接加入；若也要无链接发现，必须另行定义收件人绑定或认领机制，不能根据项目成员身份或猜测 token 推导。
5. 涉及服务端 controller/service、身份验证或收件人数据模型、前端资源 API 与项目空态/邀请列表。测试至少覆盖本人和他人隔离、未验证邮箱、无绑定邮箱、过期、撤销、已接受、归档项目、角色撤权、并发接受和现有 token 流程。是否需要数据库迁移取决于最终选择的收件人绑定方案。

后续独立能力需要决定：使用哪种可证明的收件人身份；是否展示不可接受的历史邀请及归档项目；无邮箱绑定邀请是否继续仅凭链接加入。这些决定不阻塞本次已调整范围内的邀请链接流程验收。

## #29 独立步骤名称与验收语义

### 本轮落地的真实契约

- 流程修订 `definition.steps[]` 增加可选 `displayName: string`。`key` 仍是稳定机器标识；名称不参与任务关联键、依赖键或实例绑定。没有新增任务名称快照列，也没有数据库 schema 或迁移变更。
- 字段可省略；提供时必须是字符串，去除首尾空白后为 1–120 个 Unicode code points。`null`、非字符串、空白和超长值返回 `/steps/N/displayName` 字段错误及中文提示。沿用现有名称字段的宽松字符规则，没有另加字符白名单。
- shared 导出 `WORKFLOW_STEP_DISPLAY_NAME_MAX_LENGTH` 和 `workflowStepDisplayNameOf`。验证和查询 helper 不规范化或改写定义原文，避免读取或校验改变历史 JSON/digest；Web 展示时 trim。结构化输入删除空值时省略字段，输入过程保留空格，纯空白在 blur 后省略；高级 JSON 的显式空白值由校验提示。
- 新名称随完整定义正常保存、编译和发布，新修订 digest 按现有完整定义算法计算。已有草稿自动保存/恢复、发布票据、版本号、CAS、项目权限均沿用。发布成功清理草稿；CAS 失败保留草稿和编辑内容。未知定义字段及步骤内未知字段在结构化/JSON 往返和发布 payload 中保留。
- 有名称时显示独立名称；无名称的历史定义沿用各视图已有中文 `STEP_LABELS` 映射，无法映射时显示原始 key。回退只影响展示，不回填定义。类型中文显示为“产品 / 交付 / 验证 / 发布”，提交仍为 `PRODUCT / DELIVERY / VERIFY / RELEASE`；高级 JSON 保留原枚举值。

### 修订绑定、API 投影和兼容

任务、看板、需求详情任务/评审、评审列表/详情、工作台可开工/待评审，以及流程实例创建/读取结果新增 `stepDisplayName`。服务端从任务或评审关联实例的 `definitionRevisionId` 读取对应修订，批量修订查询限定对应 `projectId`；没有名称或没有修订时返回 `null`。各 service 沿用已有项目访问检查，未授权调用不向用户返回名称。需求详情和工作台在授权后查询数据；评审详情仍先按 ID 读取记录，再按其真实项目执行授权，不改变原有调用顺序。名称不是从当前最新修订读取。

Web 在看板、需求任务列表/团队流程卡、任务评审列表及决定页、工作台和初始化流程弹窗接线。文档评审保持文档标题。项目流水线是需求阶段聚合，没有步骤标题投影，因此不虚构步骤字段。旧客户端可以忽略新增投影，旧定义无需回填；绑定旧修订的实例不会因新修订发布而改名。历史修订 JSON、digest、修订号和实例绑定均不改写。

### 验收规则的既有语义

当前角色槽位、评审槽位、`gates.reviewerSlots` 和 `ALL` 门槛可表达审批/验收归属与所有必需槽位通过；服务端按步骤类型区分任务验收和发布验收，通过实例槽位绑定确定验收人。实例创建仍检查 PRD 验收 key 的任务覆盖。

用户已确认本次沿用上述语义，不新增自由文本验收说明、`ANY` 或任意可执行条件。这些能力不等同于现有 ALL 门槛；未来如需新增，应另行定义数据、执行、权限、版本与迁移语义。

发布动作与流程定义字段需要区分：当前页面已有编译校验、票据确认、版本/CAS 发布和草稿恢复；现行流程定义的 `RELEASE` 步骤及其 `RELEASE_ACCEPTANCE` 门槛可表达发布验收，但没有另一个独立的通用 publish 配置对象。若产品所称“发布配置”还包含独立发布目标、条件或策略，需先确认字段和服务端执行语义。

接口路径说明：上述后续方案的 `/v1/...` 为省略部署全局前缀的控制器路径；当前 Web 请求经 `/api/v1/...`。本轮没有上线这些邀请发现接口；步骤名称使用现有受权限保护的业务接口增量投影。
