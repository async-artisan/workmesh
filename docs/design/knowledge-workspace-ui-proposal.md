# 三大知识库 UI 工作区设计方案（评审稿）

> 状态：方案，尚未实现。静态原型仅用于讨论结构与交互，卡片数量、文档内容、命中结果均为演示数据，不代表当前项目配置或生产统计。
> 适用范围：WorkMesh Web 的“知识库”浏览、阅读与评审入口。
> 设计目标：让使用者先认出知识类别、迅速找到可用内容，再按需查看版本和治理信息。

## 1. 背景与设计判断

当前知识页面以项目内文档列表、候选修订、版本差异和评审入口为核心。页面的文档类型（UNDERSTANDING、DECISION、PRD、KNOWLEDGE）与三大知识库类别（BUSINESS、SYSTEM、PRACTICE）是不同维度，现有界面没有把后者呈现为稳定、可理解的浏览入口。

因此，本方案把页面重心调整为“找知识—读生效内容—判断适用性—按需审阅版本”。候选审批、差异比较、撤回发布等现有工作流仍保留，但进入详情后再展示。

三类知识库在设计稿中对应不同的问题和粒度。业务规则、系统运行知识、角色操作实践不宜仅靠同一张平面表格区分；入口文案和库内导航应反映用户来这里要完成的事情。设计背景见 [知识架构](../knowledge-architecture.md) 和 [当前 UI 规范](./ui.md)。

## 2. 目标与范围

### 目标

- 在页面首屏明确呈现业务事实、系统事实、角色实践三个入口。
- 用自然语言说明每个库回答什么问题，并给出典型内容示例。
- 打开文档后优先看到当前已发布正文，明确提示候选是否生效。
- 支持在项目可见范围内查找内容，并准确说明搜索覆盖哪些内容。
- 将阅读者需要的信息放在正文附近，将治理和历史操作放在次级位置。
- 提供未启用、空库、无结果、权限受限、加载失败等不同反馈。
- 沿用 WorkMesh 现有亮色 UI v4、设计令牌、卡片和状态语义。

### 本阶段不包含

- 改变 Agent 生成候选、人工评审后发布的职责边界。
- 允许普通用户绕过评审直接编辑或发布知识。
- 实现自动捕获、复用统计、过期判定、退役等尚未交付的治理闭环。
- 通过演示原型宣称三类库、全文索引或治理字段已经上线。
- 在 UI 中静态填入真实计数、负责人、权限或文档内容。

### 页面区域

| 区域 | 用途 | 设计说明 |
| --- | --- | --- |
| 项目栏 | 确认当前查阅范围 | 放在标题和搜索附近；切换项目后清除详情和旧结果 |
| 搜索框 | 以问题或关键词查找 | 默认作用于当前项目中用户可访问的范围；提示搜索是否包含正文 |
| 三库入口卡 | 让类别可见并帮助用户选择 | 固定类别名称、用途和示例；不把文档类型混入库类别 |
| 筛选栏 | 缩小列表 | 库类别、文档类型、当前状态、适用范围分开展示 |
| 分类导航 | 显示选中库中的组织路径 | 按领域、系统单元或角色提供导航；没有数据时不显示假分类 |
| 结果列表 | 扫描候选文档 | 每项给出标题、内容摘要、类别、适用范围和发布状态 |
| 阅读区 | 直接阅读当前内容 | 保持清晰正文宽度；目录、来源和元数据辅助阅读 |
| 版本与治理 | 支持评审和历史追溯 | 在阅读区的次级标签或折叠区呈现，不挤占首屏阅读空间 |

入口卡片上的“已发布数”“待处理数”“最近更新”属于可选信息。它们只有在服务端按当前用户权限聚合后才可以展示；第一版不依赖这些计数。

## 4. 三类入口与库内体验

| 入口 | 首屏说明 | 首选导航 | 列表主要信息 | 正文重点 |
| --- | --- | --- | --- | --- |
| 业务事实库 | 了解业务概念、规则和适用边界 | 业务领域、术语、流程 | 术语/规则/流程标签、适用业务 | 规则结论、适用对象、例外、来源 |
| 系统事实库 | 了解系统组成、依赖和运行方式 | 服务、应用、数据集或工作单元 | 单元名称、文档形态、上下游提示 | 系统职责、接口、运行手册、相关决策 |
| 角色实践库 | 按角色找到当前任务的做法 | 角色、工作阶段、实践类型 | SOP/模板/检查表等类型 | 操作步骤、检查项、完成标准、模板入口 |

文档类型描述“这是什么形式的文档”；知识库类别描述“它归属于哪类知识”。筛选项和文档详情应同时区分这两个字段。

库内的领域、服务单元、角色阶段需要真实数据支撑。无对应元数据时，第一版显示“全部文档”，并允许用可用字段筛选；不得通过标题关键字伪装结构化导航。

## 5. 关键交互

### 5.1 首次进入

1. 页面加载用户有权查看的项目。
2. 用户选择项目后，展示搜索框和三类入口卡。
3. 项目下有可浏览的知识库时，展示该库入口及实际支持的导航信息。
4. 项目未配置相应类别或服务无法确认配置状态时，使用中性说明；不根据普通用户看不到的数据推断私有知识库不存在。

### 5.2 选择知识库

- 选择卡片或导航项后，该类别成为明显的当前筛选条件。
- 标题区显示完整名称，例如“系统事实库 / 支付服务”。
- “全部”入口可返回当前项目内用户可访问的内容集合。
- 所有筛选条件均可移除，列表更新后保留阅读位置的合理预期。

### 5.3 搜索与结果

- 输入问题或关键词后，在结果标题和摘要中标出命中词。
- 搜索结果明确显示所属库、文档类型和状态，避免同名文档难以区分。
- 未命中时说明当前搜索范围，并提供清除筛选或查看其他可访问类别的操作。
- 第一阶段若只支持标题、元数据和需求关联搜索，搜索框旁需明确说明“搜索标题和关联信息”；正文全文搜索列为后续能力。
- 结果数量仅代表服务端完整返回且当前用户获准查看的数据；分页必须正确续取下一页。

### 5.4 打开与阅读

- 首次打开默认选择已发布修订；详情标题附近显示“当前生效版本”。
- 没有已发布版本时显示“暂无已发布版本”；如果有候选，再引导用户进入候选说明或评审。
- 文档有新候选时，同时显示“当前生效 vN”和“候选 vN+1 · 尚未生效”，不以候选正文替代发布正文。
- 正文区使用适合阅读的窄行宽和层级排版；支持标题目录、复制链接以及适当的代码块展示。
- 来源需求、关联决策或关联知识作为可点开的引用显示，并说明是否为当前来源数据。
- 手机端进入单栏详情页，返回列表时保留筛选和搜索词。

### 5.5 历史和评审

- 阅读区提供“历史版本”与“版本差异”二级入口。
- 候选与已发布修订比较时，标出基线和目标版本，并说明候选尚未生效。
- 评审操作继续跳转现有评审页面；撤回等高风险操作保留已有确认流程。
- 用户发现遗漏或疑似过期时，可以提交“反馈问题 / 建议补充”，关联文档及当前修订。第一阶段可以把反馈路由到 Agent 返修流程；未实现反馈闭环前不展示会产生新版本的承诺。

## 6. 状态文字和可用性规则

| 状态 | 用户看到的表达 | 操作提示 |
| --- | --- | --- |
| 已发布 | “当前生效 · vN” | 可阅读、查看历史 |
| 候选 | “候选内容 · 尚未生效” | 有评审入口时显示“查看评审” |
| 候选无评审入口 | “候选内容 · 评审入口暂不可用” | 可重试加载或查看原因 |
| 已撤回 | “已撤回 · 不作为当前生效内容” | 可查看历史；是否可恢复按现有权限和流程执行 |
| 未配置或不可见 | “当前没有可浏览的此类内容” | 如服务能安全地区分未启用与无权访问，再提供准确原因 |
| 筛选无结果 | “没有匹配内容” | 清空搜索词或筛选 |
| 加载中 | 骨架或明确“正在读取” | 避免把暂时未加载显示成空库 |
| 请求失败 | “内容暂时无法读取” | 保留上下文，提供重试 |
| 权限不足 | “你当前无法查看此内容” | 不透露不可见库、文档或计数 |

类别和状态必须使用可读文字，不只使用颜色。状态数值与版本序号应和正文内容相邻，技术哈希等辅助信息收进详情。

候选状态不必然意味着评审流程已成功建立。页面根据实际评审状态提供动作；不把所有候选都笼统标成“待评审”。

## 7. 视觉与响应式建议

- 复用现有 UI v4 亮色表面和 --bg-app、--bg-panel、--border、--accent 等令牌；不引入第二套主题。
- 三卡使用一致的图标、卡片尺寸和浅色辅助标识；可用克制的颜色差异帮助辨识类别，同时保证文字本身能表达类别。
- 在宽屏中，搜索与三卡铺满上方；列表和正文并排，正文宽度优先保证阅读舒适度，页面主体限制最大宽度。
- 默认使用文档索引与正文两栏，库内分类放在索引顶部；有真实范围数据后再增加领域、单元和角色导航。
- 小屏将三卡压缩为同时可见的三个入口，保留完整类别名称和简短用途，避免第三个库藏在横向滚动之外；文档详情单栏显示，并提供返回结果。
- 正文至少 14px，表格可使用 12px；通过行高、段落间距和可滚动阅读保持舒适度，不为塞进首屏压小字体。
- 列表项不要使用表格呈现长标题和摘要；状态、适用范围和类型使用次级文字及标签。
- 键盘操作覆盖搜索、卡片切换、列表选择、返回和关闭详情；焦点轮廓清晰，触屏点击区域充足。
- 支持系统减少动态效果设置；移动端不以横向滚动作为主要阅读路径。

## 8. 数据与 API 依赖

数据库中已有知识库类别字段及文档范围、负责人、复核时间、修订置信度和证据等相关字段；但数据库字段存在不代表当前 API 已暴露或可安全展示。实施前应以 API 视图和授权行为为准复核。

| UI 能力 | 当前能力边界 | 需要的支持 |
| --- | --- | --- |
| 显示三类库 | KnowledgeBase 有 kind，当前知识库视图/API 未向 Web 提供可用类别 | API 返回授权范围内的库 kind 和稳定名称 |
| 显示文档库内适用范围 | 数据库有 scope 字段，当前文档视图未完整透出 | API 返回已授权的 scopeKind/scopeId 及可读展示名 |
| 显示责任与复核信息 | 数据库有 owner/reviewDueAt 字段，现有视图未提供 | 由服务端返回并按权限裁剪；定义空值语义 |
| 显示证据与置信度 | 修订数据存在相关模型信息，现有 Web 视图不足以构建完整证据区 | API 返回可展示的证据引用和置信度说明 |
| 跨库全文搜索 | 当前搜索接口按单个知识库搜索已发布修订 | 新增项目范围、权限过滤、正文索引、摘要片段和游标的搜索合同 |
| 全量列表与计数 | Web 当前仅读取一次文档列表；API 有游标分页 | 页面续取游标或采用服务端分页；统计由授权后的服务端聚合提供 |
| 未启用与无权限区分 | 若 API 隐藏不可见资源，Web 无法推断它们是否存在 | 如产品要求精确状态，提供不泄露私有资源存在性的安全状态合同 |

首版可以先复用已存在的授权文档数据，按已知信息实现三类导航外观和已发布正文阅读，但在 API 未返回 KnowledgeBase.kind 前，不应以文档类型推测知识库类别。若返回的数据无法区分三类，应显示“类别信息暂不可用”或暂不显示未经验证的计数。

### 8.1 P0 最小数据合同

P0 可以支持三库入口，但必须先有可靠的类别来源。最低限度由服务端按当前用户授权返回：

- 项目内可浏览的知识库标识、显示名和类别（BUSINESS/SYSTEM/PRACTICE）。
- 类别的可用性状态；缺省时采用不泄露私有库存在性的中性状态。
- 文档的知识库标识、文档类型、最新已发布修订、候选修订及真实评审入口。
- 正文内容所需的已发布 revision ID，以及正确续取列表的游标和是否有更多数据。
- 搜索/列表返回的计数，只计算权限过滤完成后的数据；没有计数时前端省略数字，不补零。

如果当前接口尚未提供库类别，前端不得按 UNDERSTANDING、DECISION、PRD、KNOWLEDGE 推断三库类别。P0 的视觉评审可以用明确标记为演示的静态内容；真实页面启用该结构前须补类别字段。

### 8.2 搜索接口分阶段

P0 以完整、诚实的项目内浏览为基础：续取现有游标，支持已载入并授权的文档标题、文档类型、需求关联和状态检索。输入框的提示文案与实际字段一一对应。

P1 如增加正文全文搜索，应约定：

- 范围是当前项目内用户可读知识库，且服务端在命中和片段生成前执行权限过滤。
- 默认结果以已发布修订为主；候选、撤回历史由清晰的范围切换控制。
- 返回知识库类别、文档类型、生效/候选提示、内容片段、命中修订和稳定游标。
- 搜索总数、分页、缓存与日志均不能暴露无权访问的数据。

搜索服务还未覆盖全部字段时，应在结果页说明范围，不能用空结果暗示“项目里没有这类知识”。

## 9. 分期建议

| 阶段 | 范围 | 验收重点 |
| --- | --- | --- |
| P0：让分类可见并改善查阅 | 三类入口文案、知识库类别最小 API 字段、选中态、筛选范围说明、列表摘要、已发布正文优先、发布/候选状态说明、续取全部分页 | 用户能回答“我在哪个库、当前读的是不是生效版、结果覆盖什么范围” |
| P1：按真实范围组织与搜索 | scope 导航、跨库全文搜索、片段高亮、来源关系、规范化的空态和访问状态 | 搜索完整性经过权限和分页验证；导航不依赖猜测 |
| P2：内容反馈和治理呈现 | 反馈到 Agent、owner、复核日期、证据/置信度、已实现的过期治理提醒 | 每个治理提示都有真实 API 字段和可执行处理路径 |

三卡的基本信息属于 P0；真实计数、负责人、复核日期、全文索引和治理提醒均不是视觉层单独可以补出的能力。

## 10. UI 验收清单

- 三个入口使用中文名称和任务说明，用户能区分业务规则、系统运行和角色做法。
- 三库类别与文档类型分开展示和筛选，不互相替代。
- 页面首屏可见项目范围、当前知识库类别、搜索入口和当前生效状态。
- 点击文档后先看到已发布正文；候选显式提示尚未生效。
- 已有评审、历史、差异和撤回入口仍能使用并遵守现有确认流程。
- 搜索提示与真实搜索字段一致；跨库搜索在接口完成前不宣称搜索正文。
- 游标分页加载完整，结果总数不会误导；授权范围外数据不进入结果、统计或缓存提示。
- 未配置、不可见、空库、无结果、加载中、失败有可区分且安全的反馈。
- 窄屏布局可读、可操作；键盘可完成入口、搜索、列表和详情的主要操作。
- 原型演示内容标注为示例数据；实施后再用真实授权数据截图和验收。

## 11. 方案假设与待评审点

1. 知识库页面的主要用户是日常查阅者，评审与版本治理是次级但必要的任务。
2. 项目作为初始搜索边界；跨项目搜索不在本方案首版范围内。
3. 三类库入口作为稳定类别设计，但每个项目实际启用哪些库由授权 API 决定。
4. Agent 仍负责生成和提出修订；人工通过已有评审流程决定发布。
5. 原型中的卡片状态和计数用于表达布局，不表示当前后端返回了完整三库数据。
6. 本方案定稿后再进入实现拆分；实施时同步检查 Web、API、权限、分页和浏览器验收。

## 12. 可评审的交互原型

## 13. 参考项目借鉴

本方案参考了几种成熟知识产品的共同做法，采用“门户 + 集合 + 阅读器”的组合，不直接复制某个产品的视觉或交互。

### Notion Wiki：先有可编辑的入口，再有完整列表

Notion 的 Wiki 默认提供 Home、All pages 和 Pages I own 三种视图；Home 用于解释这个 Wiki 包含什么内容、由哪个团队负责，并可按标题组织页面；All pages 则承担完整内容浏览。页面还可以有 owner 和验证状态，验证到期后提醒负责人重新确认。

对 WorkMesh 的借鉴是：知识库首页负责说明“这个库回答什么问题”，库内再提供“全部可浏览内容”视图；文档标题附近显示当前生效或待确认状态，责任和复核信息放在文档信息区。WorkMesh 的正文由 Agent 生成、人工评审发布，因此只借鉴入口和验证表达，不照搬自由编辑模式。

### GitBook：用集合组织空间，而不是把所有文档摊平

GitBook 将多个 Space 放进 Collection，并为 Collection 提供标题、描述和访问级别；这种结构适合先按主题、团队或用途选择一个集合，再进入集合内的文档空间。

对 WorkMesh 的借鉴是把三类知识库当成一级集合：业务事实库、系统事实库、角色实践库。进入某个库后，再按业务领域、系统单元或角色阶段组织内容。库卡片应包含用途说明和典型内容，让用户在点击前知道自己是否来对了地方。

### Slite：搜索是独立入口，结果必须带范围和权限语义

Slite 将 Search 作为左侧的独立入口，也支持快捷键；不输入关键词时展示最近编辑或查看过的文档。搜索结果只包含当前用户有权访问的文档，并可按内容类型、频道、日期、贡献者和已验证文档筛选。

对 WorkMesh 的借鉴是：搜索框放在知识库首页的第一层，空查询可以展示“最近阅读”和“最近更新”；结果中明确显示所属知识库、文档类型、当前状态和适用范围。搜索范围和结果数量必须经过服务端权限过滤，不能由前端根据缺失数据猜测“未配置”或“没有内容”。

### Backstage TechDocs：搜索结果要能说明来源和关系

Backstage Search 允许接入多个索引来源，并为不同插件定制搜索结果的外观；TechDocs 也是其支持的内容来源之一。它的价值在于让搜索结果不仅是标题，还能说明来源、类型和关联对象。

对 WorkMesh 的借鉴是：系统事实库中的文档结果可以显示服务、工作单元、接口或运行手册等上下文；跨库搜索结果要带“业务 / 系统 / 实践”的来源标签，后续再补关联需求、关联服务和证据入口。第一版先把来源标签和当前状态做清楚，不急于实现关系图。

### 适合 WorkMesh 的组合方案

借鉴后，知识库首页建议采用以下层级：

```text
项目范围
  → 全局搜索 / 最近阅读 / 最近更新
  → 三个知识集合：业务事实、系统事实、角色实践
  → 当前集合内的主题入口和代表性文档
  → 文档阅读器：正文、当前生效状态、来源
  → 次级治理：候选、差异、历史、负责人、复核信息
```

这个结构比单一文档表更适合 WorkMesh，因为它同时支持三种任务：快速找答案、按类别浏览、追溯正式依据。三类知识库仍然是 KnowledgeBase 类别，`KNOWLEDGE / PRD / UNDERSTANDING / DECISION` 仍然是文档类型，两个维度必须在界面上分别显示。

不建议直接借鉴以下做法：把所有内容做成无限层级的自由页面树；用一张复杂关系图取代标题、摘要和正文；在 API 没有返回真实数据时显示文档数量、负责人或复核日期；用颜色或“已验证”图标代替正式发布状态。

参考项目的价值在于验证信息架构方向，实际页面仍要服从 WorkMesh 的 Agent 生成、人工评审、版本发布和权限边界。
